Introduction

Test Anatomy

2. หัวใจสำคัญ 3 อย่างของการเขียนเทสต์ (AAA)

การเขียนสคริปต์เทสต์ 1 ข้อ จะประกอบไปด้วย 3 ขั้นตอนเสมอ

Arrange & Findเตรียมและค้นหา
→
Actกระทำ
→
Assertตรวจสอบ
  1. Arrange & Find (เตรียมและค้นหา): การหาปุ่ม, ช่องกรอกข้อความ โดยเราจะใช้ฟังก์ชัน page.locator() หรือ page.getByTestId()
  2. Act (กระทำ): สั่งให้ทำบางอย่าง เช่น .click() (คลิก), .fill() (พิมพ์ข้อความ)
  3. Assert (ตรวจสอบ): เช็กว่าผลลัพธ์ถูกต้องไหม โดยใช้คำสั่ง expect() เช่น expect(page).toHaveURL('/dashboard')
Directory Structure

3. โครงสร้างโปรเจกต์มาตรฐาน

วางโฟลเดอร์ e2e/ ไว้ในโปรเจกต์ React/Next.js ของเราเลย โดยแบ่งหน้าที่ทำงาน 4 ส่วนหลักชัดเจน

my-nextjs-app/
├── app/
├── components/
│
├── e2e/
│   ├── pages/          // 1. ส่วน Page Object (POM)
│   │   ├── BasePage.ts
│   │   ├── LoginPage.ts
│   │   └── DashboardPage.ts
│   ├── tests/          // 2. ส่วน Test Scripts
│   │   ├── auth.spec.ts
│   │   └── checkout.spec.ts
│   ├── fixtures/       // 3. ตัวช่วย/ข้อมูลทดสอบ
│   │   ├── custom-test.ts
│   │   └── mock-data.json
│   └── .auth/          // 4. เก็บ Session (Ignored)
│       └── user.json
│
├── playwright.config.ts
└── package.json

📄 e2e/pages/

คลาสตัวแทนหน้าเว็บ เก็บ Locator และ Actions (เช่น login(user, pass)) แก้โค้ดที่นี่ที่เดียวเวลา UI เปลี่ยน

🧪 e2e/tests/

ไฟล์สคริปต์ทดสอบ (.spec.ts) จะเรียกใช้งานจาก pages/ เท่านั้น ทำให้อ่านง่ายเหมือนภาษาคน

🧰 e2e/fixtures/

เก็บข้อมูลจำลอง (Mock Data) สำหรับเตรียมระบบก่อนเริ่มเทสต์

🔐 e2e/.auth/

แหล่งเก็บสถานะการเข้าสู่ระบบ ช่วยข้ามหน้า Login ไปได้เลย ลดเวลารันเทสต์ได้มหาศาล

The "Why"

4. ทำไมต้องแบ่งโครงสร้างแบบนี้?

โครงสร้างนี้อิงจาก Design Pattern ที่เรียกว่า Page Object Model (POM)

😫 ปัญหาเก่า

ถ้าเขียนคำสั่งหาปุ่ม ('#login-btn') ปนไปในไฟล์เทสต์ทั้ง 100 ไฟล์... วันนึง Front-end เปลี่ยน ID ปุ่ม เราต้องตามไปแก้โค้ดทั้ง 100 ไฟล์!

✅ ทางแก้ด้วย POM

แยกการหาปุ่มไปไว้ที่ e2e/pages/LoginPage.ts แค่ไฟล์เดียว ถ้า UI หรือ data-testid เปลี่ยน เราก็แก้แค่ไฟล์นี้ไฟล์เดียว จบ!

📈 รองรับการขยายตัว

แม้ในอนาคตจะมีเทสต์เป็นร้อยข้อ โค้ดก็จะเป็นระเบียบ คนไม่ได้เขียนโค้ด (เช่น QA, PM) ก็อ่านรู้เรื่อง

Example · Page Object

5. ตัวอย่างจริง: ส่วน Page Object (แยกหน้าเว็บ)

ไฟล์: e2e/pages/LoginPage.ts (เก็บแค่หน้าตาเว็บและ Actions)

import { Page, Locator } from '@playwright/test';

export class LoginPage {
    readonly page: Page;
    readonly usernameInput: Locator;
    readonly passwordInput: Locator;
    readonly submitButton: Locator;

    constructor(page: Page) {
        this.page = page;
        // 💡 ใช้ getByTestId ตามมาตรฐานของทีม!
        this.usernameInput = page.getByTestId('login-username');
        this.passwordInput = page.getByTestId('login-password');
        this.submitButton = page.getByTestId('login-submit-btn');
    }

    async login(user: string, pass: string) {
        await this.usernameInput.fill(user);
        await this.passwordInput.fill(pass);
        await this.submitButton.click();
    }
}
Example · Test Script

6. ตัวอย่างจริง: ส่วน Test Script (สคริปต์ทดสอบ)

ไฟล์: e2e/tests/auth.spec.ts (อ่านง่าย สบายตา)

import { test, expect } from '@playwright/test';
import { LoginPage } from '../pages/LoginPage';

test.describe('ทดสอบระบบ Login', () => {

    test('ล็อกอินสำเร็จด้วย User ที่ถูกต้อง', async ({ page }) => {
        const loginPage = new LoginPage(page);
        await page.goto('/login');

        // 1. Act: สั่งล็อกอิน (เรียกใช้ฟังก์ชันจาก POM)
        await loginPage.login('admin_demo', 'Password123');

        // 2. Assert: ตรวจสอบว่าเข้าหน้า Dashboard ได้ไหม
        await expect(page).toHaveURL('/dashboard');
        await expect(page.getByTestId('welcome-msg')).toBeVisible();
    });
});
Tooling

7. ตัวช่วยเขียนโค้ด (Playwright Codegen)

Playwright มีเครื่องมือบันทึกหน้าจอที่ช่วยเขียนโค้ดให้เราแบบ Real-time แค่เปิด Terminal แล้วพิมพ์:

npx playwright codegen localhost:3000

เมื่อหน้าเว็บเปิดขึ้นมา ทุกครั้งที่คุณเอาเมาส์ไปคลิก พิมพ์ข้อความ หรือเลือก Dropdown ตัว Playwright จะ Generate โค้ดดิบ (Raw Script) ให้ในหน้าต่างข้างๆ ทันที

ข้อดี

เหมาะมากสำหรับหาวิธีเขียน Locator ยากๆ (เช่น ปฏิทิน หรือ Modal) และช่วยให้คนที่เพิ่งหัดเขียน เริ่มต้นได้เร็วขึ้น

ข้อควรระวัง

โค้ดที่ได้จะยังไม่มีการตรวจสอบผลลัพธ์ (Assertion) เราต้องมาเขียนคำสั่ง expect(...) เพิ่มเองภายหลัง

Golden Rule

8. กฎเหล็ก: การนำโค้ดที่บันทึกมาใช้งาน

"ห้าม Copy โค้ดที่ได้ไปแปะในไฟล์เทสต์ .spec.ts ตรงๆ เด็ดขาด!"
เพราะจะทำให้โครงสร้าง POM ที่เราอุตส่าห์วางไว้พังทลาย เราต้องทำหน้าที่เป็น "คนคัดแยกโค้ด" ดังนี้:

โค้ดดิบ (จากเครื่องมือบันทึก)

// โค้ดนี้ทำงานได้ แต่มันไม่เป็นระเบียบ
await page.getByTestId('user').fill('admin');
await page.getByTestId('pass').fill('1234');
await page.getByTestId('btn').click();

วิธีที่ถูกต้อง (Refactor เข้า POM)

  1. ดึง Locator: เอา getByTestId ไปสร้างเป็นตัวแปรใน e2e/pages/LoginPage.ts
  2. สร้าง Action: จับมัดรวมกันสร้างฟังก์ชัน login(user, pass) ไว้ในคลาส
  3. เรียกใช้: ในไฟล์เทสต์ จะเหลือแค่คำสั่ง await loginPage.login(...)

CLI Commands

11. คำสั่งที่ควรรู้ (CLI Commands)

เปิด Terminal ที่ root ของโปรเจกต์ แล้วลองรันคำสั่งเหล่านี้:

คำสั่งใช้ทำอะไร
npx playwright testรันเทสต์ทั้งหมดแบบ Headless (ซ่อนเบราว์เซอร์ เหมาะสำหรับ CI/CD)
npx playwright test --ui🔥 แนะนำตอนเขียนโค้ด! เปิดหน้า UI ขึ้นมาให้เรากดรันทีละข้อและดูเบราว์เซอร์ขยับไปพร้อมๆ กัน
npx playwright test --debugเปิดโหมด Debugger เพื่อไล่ดูโค้ดทีละบรรทัด (Step-by-step)
npx playwright show-reportเปิดดูหน้า Report (HTML) ว่ามีเทสต์ข้อไหนผ่าน หรือพังตรงบรรทัดไหน
