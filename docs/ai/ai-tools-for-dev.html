AI ใน Workflow

AI review ใน MR / PR, สรุป issue, เขียน release note

ทำงานอัตโนมัติใน GitLab / GitHub

ชื่อและความสามารถของเครื่องมือเปลี่ยนเร็วมาก — ตรวจนโยบายบริษัทว่าทีมได้รับอนุญาตให้ใช้ตัวไหนและแพ็กเกจไหน (ณ ต.ค. 2026)

ใช้ให้ถูกงาน

งานไหนให้ AI ช่วยได้ดี / ต้องระวัง

ช่วยได้ดีมาก

  • อธิบายโค้ดเก่าที่ไม่มีคนรู้เรื่อง
  • เขียน unit test จากโค้ดที่มีอยู่
  • แปลงโค้ด / refactor ตามแบบที่กำหนด
  • SQL, regex, script, Dockerfile, CI YAML ร่างแรก
  • หาสาเหตุ error จาก stack trace
  • เขียนเอกสาร, commit message, PR description

ต้องระวังเป็นพิเศษ

  • ข้อมูลเวอร์ชันล่าสุดของ library — AI อาจรู้ข้อมูลเก่า
  • โค้ดด้าน security, auth, การเงิน
  • ตัดสินใจสถาปัตยกรรมแทนทีม
  • ตัวเลข / ข้อเท็จจริงที่ไม่มีแหล่งอ้างอิง
  • โค้ดที่ไม่มีใครในทีมเข้าใจหลัง merge
ตัวอย่างจริงจากคลังความรู้นี้: เอกสาร Background Jobs เคยเขียนว่า “BullMQ ใช้ PostgreSQL ไม่ได้” ตามข้อมูลเวอร์ชันเก่า แต่ BullMQ v6 (ก.ค. 2026) รองรับแล้ว — ทีมตรวจเจอและแก้จากเอกสารทางการ นี่คือเหตุผลที่ต้องตรวจทุกครั้ง
กฎของทีม · สำคัญที่สุด

ข้อมูลอะไรห้ามส่งให้ AI

🚫 ห้ามส่ง

  • รหัสผ่าน, API key, token, connection string จริง
  • ข้อมูลลูกค้า / พนักงาน (ชื่อ, เบอร์, เลขบัตร, ที่อยู่) — PDPA
  • ข้อมูลการเงิน, สัญญา, ข้อมูลที่บริษัทจัดเป็นความลับ
  • ไฟล์ .env, dump ฐานข้อมูล production

✅ ทำแบบนี้แทน

  • ใช้ข้อมูลตัวอย่าง / ปิดบังค่า (***, example.com)
  • ใช้เครื่องมือและบัญชีที่บริษัทอนุมัติ (แพ็กเกจที่ไม่เอาข้อมูลไป train)
  • ตั้ง agent ไม่ให้อ่านไฟล์ลับ (ignore / permission)
  • ถ้าไม่แน่ใจ ถามหัวหน้าทีมก่อนส่ง
ถ้าไม่กล้าโพสต์ข้อความนั้นลงช่องแชตของทีม ก็อย่าส่งให้ AI
Prompt

เขียน Prompt ให้ได้ผล: บริบท · งาน · ข้อจำกัด · รูปแบบ

Prompt กว้างเกินไป

เขียน API สร้างออเดอร์ให้หน่อย

ได้โค้ดทั่วไป ไม่ตรงโครงสร้างโปรเจกต์ ต้องแก้เยอะ

Prompt ที่ชัด

บริบท: .NET 10 Web API, Clean Architecture
(Domain/Application/Infrastructure/Api), EF Core,
FluentValidation, ตอบ error เป็น ProblemDetails

งาน: เพิ่ม endpoint POST /api/orders/{id}/cancel

ข้อจำกัด:
- ยกเลิกได้เฉพาะสถานะ Pending / Paid
- ถ้าจัดส่งแล้วตอบ 409
- ทำตามแบบของ CreateOrder ที่มีอยู่
- ไม่แก้ไฟล์อื่นที่ไม่เกี่ยว

รูปแบบ: แสดงไฟล์ที่เพิ่ม/แก้ + unit test ของ Domain

บริบท

stack, เวอร์ชัน, โครงสร้าง

งาน

ต้องการผลอะไร ชัดเจน 1 เรื่อง

ข้อจำกัด

กฎธุรกิจ, สิ่งที่ห้ามทำ, แบบที่ต้องตาม

รูปแบบผลลัพธ์

ไฟล์, ตาราง, ขั้นตอน, ภาษา

ใช้ได้ทันที

Prompt สำเร็จรูปที่ใช้บ่อย

งานPrompt
อธิบายโค้ด“อธิบายว่าไฟล์นี้ทำอะไร ทีละส่วน สำหรับคนเพิ่งเข้าทีม และชี้จุดที่อาจเป็น bug”
เขียนเทสต์“เขียน unit test ด้วย xUnit ให้ Order.Cancel() ครอบคลุม happy path, edge case และ error ทุกกรณี ห้ามแก้โค้ดจริง”
หาสาเหตุ error“นี่คือ stack trace และโค้ดที่เกี่ยวข้อง ให้ระบุสาเหตุที่เป็นไปได้ เรียงจากน่าจะเป็นที่สุด พร้อมวิธีตรวจสอบแต่ละข้อ”
Review“review diff นี้ตามลำดับ: ความถูกต้อง, ความปลอดภัย, performance, อ่านง่าย ระบุบรรทัดและเหตุผล”
SQL“เขียน SQL (PostgreSQL 17) หาลูกค้าที่ซื้อซ้ำภายใน 30 วัน จากตาราง orders(id, customer_id, created_at) อธิบาย index ที่ควรมี”
เอกสาร“สรุปการเปลี่ยนแปลงใน diff นี้เป็น PR description ตาม template ของทีม: ทำอะไร / ทำไม / ทดสอบอย่างไร”
Coding Agent

ทำงานกับ Coding Agent ให้ได้ผล

  1. ให้วางแผนก่อน — ขอแผนว่าจะแก้ไฟล์ไหน อย่างไร แล้วเราอนุมัติก่อนลงมือ
  2. งานละเรื่อง — แบ่งงานใหญ่เป็นงานย่อยที่ตรวจได้ (เหมือน PR เล็ก)
  3. ให้รันเทสต์ / build เอง — agent ที่เห็นผลเทสต์แก้ตัวเองได้ดีขึ้นมาก
  4. ตรวจ diff ทุกบรรทัด — ก่อน commit เสมอ ไม่ merge โดยไม่อ่าน
  5. เขียนกฎของโปรเจกต์ไว้ในไฟล์ — เช่น CLAUDE.md / AGENTS.md / instructions ของเครื่องมือ: stack, คำสั่ง build/test, coding standard, สิ่งที่ห้ามแตะ
# CLAUDE.md / AGENTS.md (ตัวอย่างย่อ)
- Stack: Next.js 16 (web/), .NET 10 (api/), PostgreSQL 17
- Test: `npm test --prefix web`, `dotnet test api`
- ต้องผ่าน lint + test ก่อนบอกว่าเสร็จ
- ห้ามอ่าน/แก้ไฟล์ .env* และโฟลเดอร์ secrets/
- ตาม convention ในเอกสาร React Essentials และ .NET Clean Architecture

ได้อะไร

เอกสาร 30+ เรื่อง ธีมเดียวกันทั้งหมด ในเวลาไม่กี่วัน

สิ่งที่ทำให้สำเร็จ

กฎเขียนเป็นไฟล์ (todo.md), template กลาง, ตรวจด้วยเครื่องมือทุกครั้ง

สิ่งที่คนยังต้องทำ

ตัดสินใจทิศทาง, ตรวจความถูกต้อง (เช่น เคส BullMQ v6), อนุมัติก่อนเผยแพร่

Verify

ตรวจผลงานของ AI อย่างไร

1. รันจริง

build, test, lint ต้องผ่าน — “ดูเหมือนถูก” ยังไม่พอ

2. เช็คเวอร์ชัน API

method / option ที่ AI ใช้มีจริงในเวอร์ชันของเราไหม (ดู docs, changelog, npm / NuGet)

3. อ่าน diff

มีไฟล์ที่ไม่ได้ขอให้แก้ไหม · ลบเทสต์ทิ้งเพื่อให้ผ่านไหม

4. Security

ตรวจสิทธิ์, validate input, ไม่มี secret ในโค้ด

5. License

โค้ดที่ดูเหมือน copy มาทั้งก้อนจาก open source — ตรวจที่มาและ license

6. เข้าใจก่อน merge

ต้องอธิบายให้ reviewer ฟังได้ว่าโค้ดทำงานอย่างไร

สรุป

กฎการใช้ AI ของทีม

  • ☐ ใช้เครื่องมือ / บัญชีที่บริษัทอนุมัติเท่านั้น
  • ☐ ไม่ส่ง secret, ข้อมูลลูกค้า, ข้อมูลลับของบริษัท
  • ☐ ให้บริบทครบ: stack, เวอร์ชัน, กฎ, รูปแบบผลลัพธ์
  • ☐ โปรเจกต์มีไฟล์กฎสำหรับ agent (CLAUDE.md / AGENTS.md)
  • ☐ รันเทสต์และอ่าน diff ทุกครั้งก่อน commit
  • ☐ ตรวจข้อมูลเวอร์ชันจากแหล่งทางการ
  • ☐ ผู้ commit รับผิดชอบโค้ดเหมือนเขียนเอง
  • ☐ แบ่งปัน prompt ที่ได้ผลให้ทีม (เก็บในคลังความรู้นี้)
