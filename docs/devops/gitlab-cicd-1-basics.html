ส่วนประกอบของ GitLab CI/CD

คำความหมายตัวอย่าง
Pipelineการทำงานทั้งชุดที่เกิดขึ้น 1 ครั้งต่อ push / MR / tagpipeline #1842

Artifactไฟล์ผลลัพธ์ของ job ที่ส่งต่อให้ job ถัดไป / ดาวน์โหลดได้dist/, test report
Cacheไฟล์ที่เก็บไว้ใช้ซ้ำข้าม pipeline เพื่อความเร็ว.npm/, ~/.nuget

เริ่มต้น

.gitlab-ci.yml ไฟล์แรก

# .gitlab-ci.yml (วางที่ root ของ repo)
stages: [test, build]

default:
  image: node:22-alpine          # ทุก job ใช้ image นี้ถ้าไม่ระบุเอง
  interruptible: true            # มี push ใหม่ → ยกเลิก pipeline เก่าได้

lint:
  stage: test
  script:
    - npm ci
    - npm run lint
    - npx tsc --noEmit

unit-test:
  stage: test
  script:
    - npm ci
    - npm test -- --run

build:
  stage: build
  script:
    - npm ci
    - npm run build
  1. commit ไฟล์นี้แล้ว push — GitLab สร้าง pipeline ให้อัตโนมัติ
  2. ดูผลที่ Build → Pipelines คลิก job เพื่อดู log ทีละบรรทัด
  3. lint กับ unit-test อยู่ stage เดียวกัน → รันพร้อมกัน
  4. build รันเมื่อ stage test ผ่านทั้งหมด
  5. job ไหน exit code ≠ 0 → pipeline แดง และ MR merge ไม่ได้ (ถ้าตั้งไว้)

ใช้ Build → Pipeline editor ใน GitLab ช่วยตรวจ syntax และดูภาพ pipeline ก่อน commit

ลำดับการทำงาน

Stage เรียงลำดับ · needs ทำให้เร็วขึ้น

แบบ stage ปกติ

testweb:test · api:test
→ รอทั้งหมด →
buildweb:build · api:build

api:build ต้องรอ web:test ทั้งที่ไม่เกี่ยวกัน

ใช้ needs

api:build:
  stage: build
  needs: [api:test]       # รอแค่ api:test
  script: [dotnet publish -c Release]

web:build:
  stage: build
  needs: [web:test]
  script: [npm run build]

แต่ละฝั่งวิ่งต่อได้ทันทีที่งานของตัวเองเสร็จ

ควบคุมว่า job รันเมื่อไร

rules: เลือกเงื่อนไขการรัน

# ระดับทั้ง pipeline: สร้าง pipeline เมื่อไร
workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG

# ระดับ job
web:test:
  rules:
    - changes: [web/**/*]           # รันเมื่อโค้ด web เปลี่ยน
  script: [npm test -- --run]

deploy:production:
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
      when: manual                  # มีปุ่มให้คนกด
  script: [./deploy.sh production]
อยากให้รันเมื่อเงื่อนไข
เปิด / อัปเดต MR$CI_PIPELINE_SOURCE == "merge_request_event"
push เข้า main$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
สร้าง tag เวอร์ชัน$CI_COMMIT_TAG
บางโฟลเดอร์เปลี่ยนchanges: [api/**/*]
ให้คนกดเองwhen: manual
ตั้งเวลา (nightly)$CI_PIPELINE_SOURCE == "schedule"
ใช้ rules แทน only / except แบบเก่า และใส่ workflow:rules เพื่อไม่ให้เกิด pipeline ซ้ำ 2 ชุดตอนมีทั้ง branch push และ MR
ตัวแปร

Variables: ที่ GitLab มีให้ และที่เราตั้งเอง

Predefined (มีให้เสมอ)ค่า
CI_COMMIT_SHORT_SHAรหัส commit 8 ตัว ใช้เป็น tag image
CI_COMMIT_REF_SLUGชื่อ branch ที่ใช้ใน URL ได้
CI_COMMIT_TAGชื่อ tag (มีเฉพาะ pipeline ของ tag)
CI_DEFAULT_BRANCHปกติคือ main
CI_REGISTRY_IMAGEที่อยู่ image ของโปรเจกต์ใน GitLab Registry
CI_REGISTRY_USER / _PASSWORDสิทธิ์ push registry ชั่วคราวต่อ job

ตัวแปรของเรา

Settings → CI/CD → Variables ใส่ secret เช่น COOLIFY_TOKEN, SSH_PRIVATE_KEY

Masked / Hidden

ซ่อนค่าใน log ของ job · Hidden ซ่อนในหน้า settings ด้วย

Protected

ส่งให้เฉพาะ branch / tag ที่ protected — กัน branch ของคนอื่นดึง secret production ไปใช้

Environment scope

ค่าเดียวกันชื่อเดียวกันแต่ต่าง environment (staging / production)

ห้าม echo หรือ env แสดง secret ใน log และห้ามใส่ secret ใน .gitlab-ci.yml ที่ commit
ทำให้เร็ว / ส่งต่อผลลัพธ์

Cache vs Artifacts

CacheArtifacts
ใช้ทำอะไรเร่งความเร็ว (ไม่มีก็ทำงานได้ แค่ช้า)ส่งผลลัพธ์ให้ job ถัดไป / ให้คนดาวน์โหลด
ตัวอย่างnpm cache, NuGet packages.next/, publish/, test report
รับประกันว่ามีไม่ (อาจไม่มีในบาง runner)ใช่ (ภายใน pipeline เดียวกัน)
web:build:
  image: node:22-alpine
  cache:
    key:
      files: [web/package-lock.json]   # lock file เปลี่ยน = cache ใหม่
    paths: [.npm/]
  script:
    - npm ci --cache .npm --prefer-offline --prefix web
    - npm run build --prefix web
  artifacts:
    paths: [web/.next/]
    expire_in: 1 day                   # อย่าเก็บนานเกินจำเป็น

Services และแสดงผลเทสต์ใน Merge Request

api:test:
  image: mcr.microsoft.com/dotnet/sdk:10.0
  services:
    - name: postgres:17-alpine
      alias: db                     # เรียกด้วย Host=db
  variables:
    POSTGRES_DB: shop_test
    POSTGRES_USER: shop
    POSTGRES_PASSWORD: test
    ConnectionStrings__Default: Host=db;Database=shop_test;Username=shop;Password=test

  artifacts:
    when: always                    # เก็บ report แม้เทสต์ fail

เครื่องที่รัน job

Runner: ใช้ของ GitLab หรือมีเครื่องของเราเอง

Shared runner (GitLab.com)

  • ใช้ได้ทันที ไม่ต้องดูแลเครื่อง
  • มีโควตานาทีต่อเดือนตามแพ็กเกจ
  • เข้าถึง server ภายในบริษัทไม่ได้

Project runner (เครื่องของเรา)

  • ไม่จำกัดนาที ใช้เครื่องแรงได้ / cache อยู่ในเครื่อง
  • deploy เข้าเครือข่ายภายในได้
  • ต้องดูแล อัปเดต และรักษาความปลอดภัยเอง
  1. Settings → CI/CD → Runners → New project runner ใส่ tag เช่น docker, internal → ได้ token ขึ้นต้น glrt-
  2. บนเครื่อง runner: ติดตั้ง GitLab Runner แล้ว gitlab-runner register --url https://gitlab.com --token glrt-… เลือก executor docker
  3. ใน job ระบุ tags: [internal] ให้ไปรันที่เครื่องนี้

วิธีลงทะเบียนแบบ registration token เดิมไม่แนะนำแล้ว ใช้ token glrt- ที่สร้างจาก UI แทน

Troubleshooting

ปัญหาที่พบบ่อย

อาการสาเหตุวิธีแก้
Pipeline ไม่ถูกสร้างYAML ผิด หรือ workflow:rules ไม่ตรงตรวจใน Pipeline editor
Job ค้าง “pending” นานไม่มี runner ที่ตรง tagsตรวจ tag ของ job กับ runner
Pipeline ซ้ำ 2 ชุดต่อ 1 pushมีทั้ง branch pipeline และ MR pipelineใช้ workflow:rules (สไลด์ 6)
ตัวแปร secret เป็นค่าว่างตั้งเป็น Protected แต่ branch ไม่ protectedprotect branch / tag หรือเอา Protected ออก (ระวัง)
ช้าเพราะติดตั้ง package ทุกครั้งไม่มี cacheตั้ง cache:key:files (สไลด์ 8)
“Job succeeded” แต่จริง ๆ ผิดscript ไม่ส่ง exit code ผิดพลาดออกมาใน shell script ใช้ set -euo pipefail
