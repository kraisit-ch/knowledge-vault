เตรียม repo

โครงสร้าง repo และการแยกไฟล์ CI

shop/
├─ .gitlab-ci.yml            # ไฟล์หลัก: stages, workflow, include
├─ ci/
│  ├─ web.gitlab-ci.yml      # job ของ Next.js
│  ├─ api.gitlab-ci.yml      # job ของ .NET
│  └─ deploy.gitlab-ci.yml   # build image + deploy
├─ web/                      # Next.js + Dockerfile
└─ api/                      # .NET solution + Dockerfile

# .gitlab-ci.yml
stages: [test, build, scan, deploy]

workflow:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG

default:
  interruptible: true

include:
  - local: ci/web.gitlab-ci.yml
  - local: ci/api.gitlab-ci.yml
  - local: ci/deploy.gitlab-ci.yml

แยกไฟล์ด้วย include ทำให้แต่ละทีมดูแลส่วนของตัวเองได้ และ review ง่าย

ci/web.gitlab-ci.yml

Job ของ Next.js

.web:                                   # template (ขึ้นต้นด้วยจุด = ไม่รันเอง)
  image: node:22-alpine
  rules:
    - changes: [web/**/*, ci/web.gitlab-ci.yml]
  cache:
    key: { files: [web/package-lock.json] }
    paths: [.npm/]
  before_script:
    - cd web
    - npm ci --cache ../.npm --prefer-offline

web:lint:
  extends: .web
  stage: test
  script:
    - npm run lint
    - npx tsc --noEmit

web:test:
  extends: .web
  stage: test
  script:
    - npx vitest run --reporter=junit --outputFile=../reports/web.xml
  artifacts:
    when: always
    reports: { junit: reports/web.xml }

extends ดึงค่าจาก template มาใช้ซ้ำ ไม่ต้องเขียน image / cache / rules ซ้ำทุก job

ci/api.gitlab-ci.yml

Job ของ .NET

.api:
  image: mcr.microsoft.com/dotnet/sdk:10.0
  rules:
    - changes: [api/**/*, ci/api.gitlab-ci.yml]
  variables:
    NUGET_PACKAGES: $CI_PROJECT_DIR/.nuget
  cache:
    key: { files: [api/Directory.Packages.props] }
    paths: [.nuget/]

api:test:
  extends: .api
  stage: test
  services:
    - name: postgres:17-alpine
      alias: db
  variables:
    POSTGRES_DB: shop_test
    POSTGRES_USER: shop
    POSTGRES_PASSWORD: test
    ConnectionStrings__Default: Host=db;Database=shop_test;Username=shop;Password=test
  script:
    - cd api
    - dotnet format --verify-no-changes
    - dotnet build -warnaserror
    - dotnet test --no-build --logger "junit;LogFilePath=../reports/{assembly}.xml"
  artifacts:
    when: always
    reports: { junit: reports/*.xml }

NUGET_PACKAGES

ย้ายที่เก็บ package มาไว้ในโฟลเดอร์โปรเจกต์ เพื่อให้ cache ได้

ci/deploy.gitlab-ci.yml

Build และ Push Docker Image เข้า GitLab Registry

.docker-build:
  stage: build
  image: docker:29
  services: [docker:29-dind]           # Docker-in-Docker (runner ต้องเปิด privileged)
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  before_script:
    - echo "$CI_REGISTRY_PASSWORD" | docker login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
  script:
    - IMAGE="$CI_REGISTRY_IMAGE/$APP"
    - TAG="${CI_COMMIT_TAG:-sha-$CI_COMMIT_SHORT_SHA}"   # tag เวอร์ชัน หรือ sha
    - docker pull "$IMAGE:latest-main" || true            # ใช้ layer เดิมเป็น cache
    - docker build --cache-from "$IMAGE:latest-main" $BUILD_ARGS -t "$IMAGE:$TAG" -t "$IMAGE:latest-main" "$APP"
    - docker push "$IMAGE:$TAG"
    - if [ -z "$CI_COMMIT_TAG" ]; then docker push "$IMAGE:latest-main"; fi
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - if: $CI_COMMIT_TAG

build:api:
  extends: .docker-build
  variables: { APP: api }

build:web:
  extends: .docker-build
  variables:
    APP: web
    BUILD_ARGS: --build-arg NEXT_PUBLIC_SITE_URL=$NEXT_PUBLIC_SITE_URL

Kaniko ที่เคยนิยมใช้ build บน runner ที่ไม่มีสิทธิ์ privileged ถูก archive แล้ว (2025) ถ้าเปิด privileged ไม่ได้ ใช้ Buildah หรือ runner ของเราเองที่ mount Docker socket แทน · ค่า NEXT_PUBLIC_* ต้องส่งตอน build (Docker ตอนที่ 4)

Security Scanning

เพิ่มการสแกนความปลอดภัยด้วย template ของ GitLab

include:
  - template: Jobs/SAST.gitlab-ci.yml
  - template: Jobs/Secret-Detection.gitlab-ci.yml
  - template: Jobs/Container-Scanning.gitlab-ci.yml

container_scanning:
  stage: scan
  variables:
    CS_IMAGE: $CI_REGISTRY_IMAGE/api:sha-$CI_COMMIT_SHORT_SHA
Scannerหาอะไร
SASTช่องโหว่ในโค้ด เช่น SQL injection
Secret Detectionรหัสผ่าน / token ที่เผลอ commit
Container Scanningช่องโหว่ใน base image และ package ของ OS
Dependency Scanningช่องโหว่ใน npm / NuGet package
scanner ใช้ได้ทุกแพ็กเกจ แต่หน้ารวมผลใน MR และ Security Dashboard แบบเต็มเป็นของแพ็กเกจ Ultimate — แพ็กเกจอื่นดูผลจาก artifact ของ job ได้ หรือใช้ Trivy เองตาม Docker ตอนที่ 7
Deploy อัตโนมัติ

Deploy staging: 2 วิธีที่ใช้บ่อย

A. สั่ง Coolify ผ่าน API

deploy:staging:
  stage: deploy
  image: curlimages/curl:latest
  environment:
    name: staging
    url: https://staging.shop.example.com
  script:
    - >
      curl --fail -X POST
      -H "Authorization: Bearer $COOLIFY_TOKEN"
      "$COOLIFY_URL/api/v1/deploy?uuid=$COOLIFY_APP_UUID"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH

Coolify ตั้งให้ดึง image tag ล่าสุดจาก GitLab Registry แล้ว CI แค่สั่งให้ deploy

B. SSH เข้า server + Docker Compose

deploy:staging:
  stage: deploy
  image: alpine:3
  environment: { name: staging, url: https://staging.shop.example.com }
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - echo "$SSH_PRIVATE_KEY" | ssh-add -
    - mkdir -p ~/.ssh && echo "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
  script:
    - ssh deploy@$STAGING_HOST "cd /srv/shop && TAG=sha-$CI_COMMIT_SHORT_SHA docker compose pull && TAG=sha-$CI_COMMIT_SHORT_SHA docker compose up -d"

compose บน server ใช้ image: …/api:${TAG} · user deploy มีสิทธิ์เฉพาะที่จำเป็น

Production

Production: กดยืนยัน และ Rollback ได้

deploy:production:
  stage: deploy
  extends: .deploy-coolify          # template จากสไลด์ 8 (ย้าย script ไปไว้ใน .deploy-coolify)
  environment:
    name: production
    url: https://shop.example.com
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
      when: manual                  # มีปุ่ม ▶ ให้กด
  resource_group: production        # deploy ทีละครั้ง ไม่ชนกัน

Protected environment

Settings → CI/CD → Protected environments กำหนดว่าใครกด deploy production ได้

Rollback

Operate → Environments → production → เลือก deployment ก่อนหน้า → Re-deploy (ใช้ image tag เดิมที่ immutable)

Database migration

รันเป็น job แยกก่อน deploy และต้องย้อนกลับได้ — rollback image ไม่ได้ย้อนข้อมูล (Docker ตอนที่ 7)

สรุป

Checklist Pipeline ก่อนใช้จริง

  • ☐ MR: lint + test + build ผ่านก่อน merge
  • ☐ image tag แบบ immutable (sha-… / 1.4.2)
  • ☐ scan secret / ช่องโหว่ อย่างน้อยบน main
  • ☐ staging deploy อัตโนมัติ + มี URL ใน Environment
  • ☐ production: tag + manual + protected environment
  • ☐ secret ใน CI/CD Variables แบบ Masked + Protected
  • ☐ migration แยก job และย้อนกลับได้
  • ☐ ทดลอง rollback จริงอย่างน้อย 1 ครั้ง
  • ☐ แจ้งผล deploy เข้าช่องทีม (Integrations → Slack / Teams)
  • ☐ pipeline ใช้เวลาไม่เกิน ~10 นาที
