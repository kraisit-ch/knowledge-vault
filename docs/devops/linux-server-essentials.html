Linux Server
พื้นฐานที่ Dev ต้องรู้

ตั้งแต่เข้า server ด้วย SSH key อย่างปลอดภัย, จัดการ user, firewall, อัปเดตระบบ, ดู log และทรัพยากร ไปจนถึงการตั้งงานอัตโนมัติ เพื่อดูแล VPS ที่รัน Docker / Coolify ได้ด้วยตัวเอง

server ที่ดีคือ server ที่ “ไม่มีใครต้อง SSH เข้าไปแก้มือ” แต่เมื่อจำเป็นต้องเข้า ต้องรู้ว่าดูอะไรก่อน
เข้า server อย่างปลอดภัย

SSH ด้วย Key แทนรหัสผ่าน

# 1) บนเครื่องเรา: สร้าง key (ทำครั้งเดียว)
ssh-keygen -t ed25519 -C "you@company.com"

# 2) ส่ง public key ขึ้น server
ssh-copy-id deploy@203.0.113.10

# 3) เข้า server
ssh deploy@203.0.113.10

# ~/.ssh/config บนเครื่องเรา — ไม่ต้องจำ IP
Host shop-staging
    HostName 203.0.113.10
    User deploy
    IdentityFile ~/.ssh/id_ed25519

# ใช้งาน
ssh shop-staging

Private key อยู่กับเราเท่านั้น

ไฟล์ id_ed25519 ห้ามส่งใคร ห้าม commit ตั้งรหัสผ่าน key ด้วย

Public key แจกได้

id_ed25519.pub ใส่ใน ~/.ssh/authorized_keys ของ server

คนออกจากทีม

ลบ public key ของคนนั้นออกจาก server ทุกเครื่องทันที

Hardening

ตั้งค่า SSH ให้ปลอดภัย (ทำหลังใส่ key แล้ว)

# /etc/ssh/sshd_config.d/99-hardening.conf
PermitRootLogin no
PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3

sudo sshd -t                 # ตรวจ config ก่อน (ไม่มี output = ผ่าน)
sudo systemctl reload ssh    # โหลด config ใหม่

# ติดตั้ง fail2ban: บล็อก IP ที่เดารหัสผิดซ้ำ ๆ
sudo apt install fail2ban
เปิด terminal ค้างไว้ 1 หน้าต่างเสมอ ขณะแก้ SSH แล้วทดสอบเข้าจากหน้าต่างใหม่ ถ้าตั้งผิดจะยังแก้กลับได้ ไม่โดนล็อกออกจาก server
Users & Permissions

User และสิทธิ์: ไม่ทำงานด้วย root

# สร้าง user สำหรับ deploy
sudo adduser deploy
sudo usermod -aG docker deploy      # ให้สั่ง docker ได้ (เทียบเท่า root — ระวัง)

# user สำหรับคนในทีม ที่ต้อง sudo
sudo adduser somchai
sudo usermod -aG sudo somchai

# สิทธิ์ไฟล์
ls -l /srv/shop
sudo chown -R deploy:deploy /srv/shop
chmod 600 /srv/shop/.env            # อ่าน/เขียนได้เฉพาะเจ้าของ
สิทธิ์เลขใช้กับ
rw-------600.env, private key
rw-r--r--644ไฟล์ config ทั่วไป
rwxr-xr-x755โฟลเดอร์, script ที่รันได้
rwxrwxrwx777ห้ามใช้ ทุกคนแก้ได้
Network

Firewall ด้วย ufw

sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH          # สำคัญ: อนุญาต SSH ก่อนเปิด!
sudo ufw allow 80,443/tcp       # เว็บ
sudo ufw enable
sudo ufw status verbose

Docker ข้าม ufw

port ที่ ports: ใน compose ถูกเปิดสู่ภายนอก แม้ ufw บล็อก เพราะ Docker แก้ iptables เอง → ผูกกับ 127.0.0.1: หรือไม่ publish port ของ DB

Firewall ของ cloud

ใช้ Security Group / Cloud Firewall ของผู้ให้บริการอีกชั้น เปิดเฉพาะ 22 (จาก IP บริษัท), 80, 443

Patching

อัปเดตระบบและ Security Patch

# อัปเดตเอง
sudo apt update && sudo apt upgrade -y

# ให้ติดตั้ง security update อัตโนมัติ
sudo apt install unattended-upgrades
sudo dpkg-reconfigure -plow unattended-upgrades

# ต้อง reboot ไหม?
[ -f /var/run/reboot-required ] && echo "ต้อง reboot"

ใช้ Ubuntu LTS

เวอร์ชัน LTS ได้ security update 5 ปี เลือก LTS ล่าสุดที่ผู้ให้บริการรองรับ

Docker image ต้องอัปเดตด้วย

อัปเดต OS ไม่ได้อัปเดตของใน container → rebuild image เป็นระยะ (Docker ตอนที่ 7)

นัดเวลา reboot

kernel ใหม่ต้อง reboot เลือกช่วงคนใช้น้อย และแจ้งทีม

Services & Logs

systemd และ journalctl: ดูสถานะและ log ของ service

systemctl status docker          # รันอยู่ไหม error อะไร
sudo systemctl restart docker
sudo systemctl enable docker     # เปิดอัตโนมัติเมื่อ boot

journalctl -u docker -f          # log ของ service แบบ real-time
journalctl -u ssh --since "1 hour ago"
journalctl -p err -b             # เฉพาะ error ตั้งแต่ boot ล่าสุด

# log ของแอปใน container
docker compose -f /srv/shop/compose.yaml logs --tail 200 -f api
ไฟล์ log ที่ควรรู้มีอะไร
/var/log/auth.logการ login / sudo (ดูคนพยายามเจาะ)
/var/log/sysloglog รวมของระบบ
journalctllog ของ service ทั้งหมดที่ systemd ดูแล
/var/log/nginx/access / error log (ถ้าใช้ Nginx บนเครื่อง)
Troubleshooting

เว็บช้า / ล่ม: ดูทรัพยากรเครื่องก่อน

uptime                      # load average (เทียบกับจำนวน CPU)
free -h                     # RAM / swap
df -h                       # พื้นที่ดิสก์ (เต็ม 100% = หลายอย่างพัง)
sudo du -sh /var/lib/docker # Docker ใช้ไปเท่าไร
htop                        # process ที่กิน CPU / RAM
docker stats                # ราย container

# หาไฟล์ใหญ่
sudo du -ah / 2>/dev/null | sort -rh | head -20

# ใครฟัง port ไหน
sudo ss -tulpn
อาการดูที่สาเหตุที่พบบ่อย
ทุกอย่างช้าuptime, htopCPU เต็ม, process วนลูป
container ถูก kill (137)free -h, dmesgRAM ไม่พอ (OOM)
เขียนไฟล์ / DB ไม่ได้df -hดิสก์เต็มจาก log / image เก่า
เข้าเว็บไม่ได้ss -tulpn, ufw statusservice ไม่ฟัง port / firewall
Automation

งานตั้งเวลา และ Backup

# crontab -e  (ของ user deploy)
# นาที ชม. วัน เดือน วันในสัปดาห์
0 2 * * *  /srv/shop/scripts/backup-db.sh >> /var/log/shop-backup.log 2>&1
0 4 * * 0  docker image prune -af --filter "until=168h"

#!/usr/bin/env bash
# /srv/shop/scripts/backup-db.sh
set -euo pipefail
FILE="/srv/backup/shop-$(date +%F).dump"
docker compose -f /srv/shop/compose.yaml exec -T db pg_dump -U shop -Fc shop > "$FILE"
find /srv/backup -name 'shop-*.dump' -mtime +14 -delete   # เก็บ 14 วัน
# ส่งสำเนาออกนอกเครื่อง (S3 / storage อื่น) — backup ในเครื่องเดียวไม่พอ

สรุป

Checklist ตั้ง Server ใหม่

  • ☐ Ubuntu LTS ล่าสุด · ตั้ง timezone Asia/Bangkok และ hostname
  • ☐ user สำหรับคน + user deploy · เข้าด้วย SSH key
  • ☐ ปิด root login และ password login · ติดตั้ง fail2ban
  • ☐ ufw + cloud firewall เปิดเฉพาะ 22 / 80 / 443
  • ☐ unattended-upgrades สำหรับ security patch
  • ☐ Docker + compose · DB ไม่ publish port ออกนอกเครื่อง
  • ☐ จำกัดขนาด log ของ Docker (Docker ตอนที่ 7)
  • ☐ backup อัตโนมัติ + สำเนานอกเครื่อง + ทดสอบ restore
  • ☐ monitoring: disk, RAM, uptime ของเว็บ + แจ้งเตือน
  • ☐ จดรายละเอียด server ไว้ในเอกสารทีม (ไม่รวมรหัสผ่าน)
