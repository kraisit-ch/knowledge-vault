คำตอบสั้น

BullMQ ต้องมี Redis (หรือตัวที่ทำงานเหมือน Redis)

BullMQ ไม่มีที่เก็บข้อมูลของตัวเอง ทุกอย่าง — งาน, สถานะ, เวลาที่ต้องรอ, ลำดับความสำคัญ — ถูกเก็บใน Redis

List / Sorted Set

คิวงานที่รอ และงานที่ต้องหน่วงเวลา (เรียงตามเวลา)

Hash

ข้อมูลของแต่ละ job: data, จำนวนครั้งที่ลอง, สาเหตุที่ล้ม

Lua script

ย้ายสถานะงานแบบ “ทำทีเดียวจบ” ไม่ให้ worker 2 ตัวหยิบงานเดียวกัน

Streams

ส่ง event completed / failed / progress ให้ QueueEvents

ใช้ PostgreSQL, SQL Server หรือ MongoDB แทน Redis ใน BullMQ ไม่ได้ ถ้าไม่อยากมี Redis ต้องเปลี่ยนไปใช้ library อื่น (สไลด์ 4)
ทางเลือกที่ 1 · ยังใช้ BullMQ

ใช้ “Redis-compatible” ตัวอื่นแทน Redis ได้

ตัวเลือกใช้กับ BullMQหมายเหตุ
Valkeyได้fork แบบ open source ของ Redis (Linux Foundation) ใช้แทนกันได้ตรง ๆ
Managed Redis (AWS ElastiCache / MemoryDB, Azure Cache, Redis Cloud)ได้ไม่ต้องดูแล server เอง ตรวจว่าตั้ง noeviction ได้
Dragonflyได้ (ต้องตั้งค่า)เร็ว ใช้ RAM น้อย ต้องรันด้วย --cluster_mode=emulated --lock_on_hashtags และตั้ง prefix คิวแบบ {bull}
Upstash Redis (serverless)ได้ แต่ระวังค่าใช้จ่ายคิดเงินต่อคำสั่ง worker ที่รอตลอดเวลาทำให้ค่าใช้จ่ายสูง
Redis Clusterได้ (ต้องตั้ง prefix)ใส่ hash tag ใน prefix เช่น {bull} ให้ key ของคิวอยู่ node เดียวกัน
Memcached / DB ทั่วไปไม่ได้ไม่รองรับคำสั่งและ Lua script ที่ BullMQ ต้องใช้

ไม่ว่าตัวไหน ต้องตั้ง maxmemory-policy noeviction และเปิด persistence (AOF) ไม่งั้น job อาจหายเงียบ ๆ (ดู BullMQ Deep Dive)

ทางเลือกที่ 2 · เปลี่ยน library (Node.js / Next.js)

ไม่อยากมี Redis เลย ใช้อะไรแทน BullMQ ได้

เครื่องมือเก็บงานที่จุดเด่นเหมาะกับ
pg-bossPostgreSQLretry, delay, cron, priority ครบ · ใช้ DB เดิมมี Postgres อยู่แล้ว ไม่อยากเพิ่ม server
Graphile WorkerPostgreSQLเร็ว เพิ่มงานจาก SQL / trigger ได้อยากสร้างงานจากใน DB โดยตรง
AgendaMongoDBเน้นงานตั้งเวลาทีมที่ใช้ MongoDB
Inngest / Trigger.devบริการ cloud (มี self-host)ไม่ต้องมี worker ค้าง ทำงานหลายขั้นได้Next.js บน Vercel / serverless
Cloud queue (AWS SQS, Google Cloud Tasks, Azure Queue)ผู้ให้บริการ cloudไม่ต้องดูแลเลย ขยายได้ไม่จำกัดแอปที่อยู่บน cloud นั้นอยู่แล้ว
RabbitMQRabbitMQข้ามภาษาได้ (.NET ↔ Node)งานต้องส่งให้ worker คนละภาษา

ตัวอย่างโค้ด · PostgreSQL แทน Redis

งานเดียวกับ BullMQ แต่ใช้ pg-boss

// lib/jobs.ts
import PgBoss from "pg-boss";

export const boss = new PgBoss(process.env.DATABASE_URL!);
await boss.start();                         // สร้างตาราง pgboss.* ให้เอง
await boss.createQueue("email");

// เพิ่มงาน (เทียบ queue.add ของ BullMQ)
await boss.send("email", { orderId: "ORD-1234" }, {
  retryLimit: 5,
  retryDelay: 2,          // วินาที
  retryBackoff: true,     // เว้นนานขึ้นเรื่อย ๆ
  singletonKey: "order-confirmation:ORD-1234", // กันเพิ่มซ้ำ
});

// worker.ts (process แยกจาก Next.js)
await boss.work("email", async ([job]) => {
  await mailer.sendOrderConfirmation(job.data.orderId);
});                                         // throw = ลองใหม่ตาม retryLimit

// งานตั้งเวลา (เทียบ Job Scheduler)
await boss.schedule("daily-report", "0 8 * * *", {}, { tz: "Asia/Bangkok" });

Queue Job vs Batch Job

Queue JobBatch Job
เริ่มเมื่อมีเหตุการณ์ (ทีละรายการ)ถึงรอบเวลา (ทีละก้อนใหญ่)
ขนาดงานต่อครั้งเล็ก: 1 ออเดอร์, 1 อีเมลใหญ่: ทุกรายการของวัน / เดือน
ผลลัพธ์เร็วแค่ไหนไม่กี่วินาทีได้ผลหลังรันจบ (นาที–ชั่วโมง)
เมื่อล้มเหลวลองใหม่เฉพาะงานนั้นต้องรู้ว่าทำไปถึงไหน แล้วทำต่อจากจุดนั้น (checkpoint)
ภาระระบบกระจายตลอดวันหนักเป็นช่วง มักรันกลางคืน
ตัวอย่างส่งอีเมลยืนยันออเดอร์ทันทีปิดยอดขายสิ้นวัน 2 ล้านรายการ, กระทบยอดธนาคาร
ใช้ร่วมกันได้: Batch ใหญ่มักถูกแตกเป็น Queue Job ย่อย เช่น job ตั้งเวลา 01:00 อ่านรายการทั้งหมด แล้วเพิ่มงานย่อยทีละ 1,000 รายการ ให้ worker หลายตัวช่วยทำและ retry เฉพาะชุดที่ล้ม

Cron บน server vs Job Scheduler ในระบบคิว

Cron ของ OS / Windows Task Scheduler / SQL AgentJob Scheduler (BullMQ, Hangfire, pg-boss)
มีหลายเครื่อง (scale)รันซ้ำทุกเครื่องรันครั้งเดียว
ล้มเหลวแล้วลองใหม่ต้องเขียนเองมีในตัว
ดูประวัติ / ผลลัพธ์ดู log เองdashboard
เครื่องดับตอนถึงเวลารอบนั้นหายไปworker ตัวอื่นทำแทน
ตั้งค่าง่าย ไม่ต้องมีอะไรเพิ่มต้องมี queue / storage

Cron ธรรมดาเหมาะกับ

งานดูแลเครื่อง: ลบไฟล์ temp, หมุน log, backup เครื่องเดียว

Job Scheduler เหมาะกับ

งานธุรกิจ: ส่งรายงาน, เตือนลูกค้า, sync ข้อมูล ที่ต้องไม่ซ้ำและต้องสำเร็จ

ทางลัดที่ต้องรู้ข้อจำกัด

Fire-and-forget: รันเบื้องหลังในแอปเดียวกัน

// Next.js 15+: ทำงานต่อหลังส่ง response แล้ว
import { after } from "next/server";

export async function POST(req: Request) {
  const order = await createOrder(await req.json());
  after(() => analytics.track("order_created", order.id)); // ไม่สำคัญ หายได้
  return Response.json(order);
}

// .NET: อย่าใช้ Task.Run ลอย ๆ ใน controller
// ให้ใช้ Channel + BackgroundService (หรือ Hangfire ถ้างานห้ามหาย)
await _channel.Writer.WriteAsync(new TrackEvent(order.Id), ct);

ใช้ได้กับ

  • ส่ง analytics / log ที่หายได้บ้าง
  • ล้าง cache
  • งานสั้น ไม่กี่วินาที

ห้ามใช้กับ

  • ส่งอีเมลยืนยัน, ตัดเงิน, ตัดสต็อก
  • งานที่ต้อง retry
  • งานยาว — deploy / restart แล้ว งานหายโดยไม่มีใครรู้

ตัวอย่างระบบจริง

ระบบ E-commerce เดียว ใช้งานเบื้องหลังหลายแบบ

  1. Queue Job: ลูกค้าสั่งซื้อ → เพิ่มงานส่งอีเมล / LINE ทันที ล้มก็ลองใหม่ 5 ครั้ง
  2. Scheduled: 08:00 ทุกวัน → สร้างรายงานยอดขายส่งผู้บริหาร
  3. Batch: 01:00 ทุกคืน → กระทบยอดกับธนาคาร แตกเป็นชุดละ 1,000 รายการ
  4. Stream: ทุกออเดอร์ → Kafka → dashboard ยอดขาย real-time
  5. Workflow: ขอคืนสินค้า → รอส่งคืน 7 วัน → ตรวจ → โอนเงิน
  6. Fire-and-forget: บันทึกว่าลูกค้าดูหน้าไหน (หายได้บ้างไม่เป็นไร)
เริ่มจากเครื่องมือเดียวที่ทำ Queue + Scheduled ได้ (BullMQ / pg-boss / Hangfire) ก็ครอบคลุมงานส่วนใหญ่แล้ว เพิ่ม Workflow engine หรือ Kafka เมื่อมีความต้องการจริงเท่านั้น
