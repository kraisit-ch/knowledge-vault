Design Principles

9 หลักการออกแบบ Retry

1. จำกัดจำนวนครั้ง

maxRetries 3–5 ครั้ง

2. เว้นระยะก่อนลองใหม่

ไม่ retry ทันทีติด ๆ กัน

3. Backoff

เพิ่มเวลารอ 1s → 2s → 4s

4. Jitter

สุ่มเวลารอเล็กน้อย ไม่ให้ทุก worker ลองพร้อมกัน

5. แยก transient / permanent

business error ไม่ retry

6. ครบแล้วส่ง DLT

ไม่ให้ message ค้างขวางตัวอื่น

7. เก็บ attempt count

รู้เสมอว่าลองไปกี่ครั้งแล้ว

8. Idempotency

ทำซ้ำแล้วข้อมูลไม่เสีย

9. Monitor retry rate

retry เยอะผิดปกติ = สัญญาณปัญหา

เว้นจังหวะให้ถูก

// retry.ts
export function backoffMs(attempt: number, baseMs = 1_000, maxMs = 30_000) {
  const exp = Math.min(maxMs, baseMs * 2 ** (attempt - 1)); // 1s, 2s, 4s, ...
  const jitter = 0.8 + Math.random() * 0.4;                 // ±20%
  return Math.round(exp * jitter);
}

export const sleep = (ms: number) => new Promise((r) => setTimeout(r, ms));
ทำไมต้อง jitter: gateway ล่ม 1 นาที worker 20 ตัวที่ fail พร้อมกันจะ retry พร้อมกันทุกรอบ แล้วถล่ม gateway ทันทีที่กลับมา การสุ่มช่วยกระจายจังหวะให้ห่างกัน

3. DLT หลัง Retry ครบ

fail → retry 1, 2, 3 → ยัง fail → publish DLT พร้อม payload เดิมและเหตุผล

ทุกเทคนิคต้องจบที่ DLT เสมอ

4. Manual Retry / Replay

admin เห็นใน DLT Inspector ว่า fail เพราะ gateway ล่ม → gateway กลับมา → กด Retry → publish กลับ topic เดิม

ต้อง: แก้ข้อมูลผิดก่อน, กันซ้ำ, audit ว่าใครกดเมื่อไร

หลักเลือก: รอ ไม่กี่วินาที → retry ใน consumer · รอ เป็นนาที หรือห้ามขวางงานอื่น → retry topic

ตัวอย่างโค้ด (KafkaJS)

Worker ที่ retry ถูกประเภทและจบที่ DLT

const MAX_RETRIES = 3;

await consumer.run({
  eachMessage: async ({ topic, partition, message }) => {
    const meta = { topic, partition, offset: message.offset, key: message.key?.toString() };

    // 1) ข้อมูลผิด → DLT ทันที ไม่ retry
    const parsed = safeParseOrder(message.value);            // JSON.parse + Zod (ไม่ throw)
    if (!parsed.success) return sendToDlt(message, meta, { type: "INVALID", reason: parsed.error, attempt: 0 });

    for (let attempt = 1; attempt <= MAX_RETRIES; attempt++) {
      try {
        await inventoryService.reserve(parsed.data);           // business logic (ตอนที่ 4)
        await publish("order-confirmed", parsed.data, meta);
        return;                                                // ✅ สำเร็จ → KafkaJS commit offset ให้
      } catch (err) {
        const last = attempt === MAX_RETRIES;
        if (!isRetryable(err) || last) {
          return sendToDlt(message, meta, { type: isRetryable(err) ? "TRANSIENT" : "BUSINESS", reason: String(err), attempt });
        }
        await sleep(backoffMs(attempt));                       // ⏳ 1s, 2s (+jitter)
      }
    }
  },
});
อย่าปล่อยให้ error หลุดออกจาก eachMessage โดยไม่ตั้งใจ: KafkaJS จะไม่ commit และอ่าน message เดิมซ้ำวนไปเรื่อย ๆ ให้จัดการเองแล้วจบด้วยสำเร็จหรือ DLT

// lib/dlt.ts
export async function sendToDlt(msg: KafkaMessage, meta: Meta, f: Failure) {
  await producer.send({
    topic: "order-events-dlt",
    messages: [{
      key: msg.key,                       // key เดิม
      value: msg.value,                   // payload เดิม
      headers: {
        ...msg.headers,                   // รวม correlation id เดิม
        "x-failed-service": SERVICE_NAME,
        "x-error-type": f.type,
        "x-error-reason": f.reason.slice(0, 500),
        "x-retry-count": String(f.attempt),
        "x-original-topic": meta.topic,
        "x-original-partition": String(meta.partition),
        "x-original-offset": meta.offset,
      },
    }],
  });
  await trackingLog.write({ ...meta, event: "SENT_TO_DLT", ...f }); // ตอนที่ 3
}

Trade-off

Retry กับลำดับข้อมูล: ต้องเลือก

partition 0

offset 10order A · กำลัง retry
←
offset 11order B · รอ
←
offset 12order C · รอ

ลำดับสำคัญกว่า

ใช้ retry ใน consumer เดิม ยอมให้ B, C รอ A

เช่น event ของบัญชีเดียวกัน (ฝาก → ถอน) ห้ามสลับ

ความเร็วสำคัญกว่า

ใช้ retry topic ให้ B, C ไปต่อได้ทันที

ยอมรับว่า A อาจถูกประมวลผลทีหลัง B — consumer ต้องรับมือ event มาไม่เรียงได้

Kafka รับประกันลำดับ ภายใน partition เดียว เท่านั้น และลำดับจะถูกต้องก็ต่อเมื่อใส่ message key (ตอนที่ 1)

Production ควรมี

  • ☐ แยก retryable / non-retryable ด้วย error class
  • ☐ exponential backoff + jitter
  • ☐ Notification มี retry (ส่งอีเมลล้มบ่อย)
  • ☐ DLT headers ครบ + retention 14–30 วัน
  • ☐ หน้า DLT Inspector พร้อม audit การกด retry
  • ☐ ทุก consumer idempotent
  • ☐ alert: retry rate, DLT count, lag
