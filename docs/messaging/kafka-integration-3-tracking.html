Message Status & Tracking
รู้ได้อย่างไรว่าสำเร็จหรือ fail

Kafka ไม่มี status ให้ message แต่ละตัว ตอนนี้จะสร้าง Tracking Log ที่ตอบได้ว่า order นี้ไปถึงไหน, fail เพราะอะไร, retry กี่ครั้ง และงานค้างอยู่เท่าไร

ความเข้าใจผิดที่พบบ่อย

Kafka ไม่มี field status แบบ PENDING / SUCCESS / FAILED

สิ่งที่ Kafka เก็บความหมาย
topicmessage อยู่ใน stream ไหน
partitionอยู่ partition ไหน
offsetลำดับภายใน partition
consumer group offsetgroup นี้อ่านถึง offset ไหนแล้ว
headersmetadata เช่น trace id, failed service
valuepayload จริง เช่น order JSON

แปลว่าอะไร

Kafka รู้แค่ว่า message “ถูกอ่านไปแล้วหรือยัง” แต่ไม่รู้ว่าอ่านแล้ว ทำงานสำเร็จหรือไม่

ถ้าต้องการสถานะ → ต้องทำ Tracking Log เอง ในโค้ดของ worker แต่ละตัว

Offset ≠ Status

ทำไม Offset ยังไม่พอ

topic:     order-events
partition: 0
offset:    42

inventory-group commit offset 43 แล้ว
→ แปลว่า: inventory-group อ่าน offset 42 ผ่านไปแล้ว

แต่ยังตอบไม่ได้ว่า…

  • ตัด stock สำเร็จไหม
  • ส่งต่อไป order-confirmed สำเร็จไหม
  • fail เพราะ business rule หรือ system error
  • retry ไปกี่ครั้ง
  • order นี้ไปถึง Payment / Notification หรือยัง
offset ที่ commit แล้วอาจเป็น message ที่ ถูกส่งเข้า DLT ก็ได้ เพราะเมื่อส่ง DLT เสร็จ worker ก็ commit แล้วไปต่อ — offset จึงบอกได้แค่ “ผ่านมือแล้ว”

Tracking Log

รูปแบบ Tracking Log ที่แนะนำ

{
  "messageId": "ORD-1234",
  "correlationId": "ORD-1234",
  "orderId": "ORD-1234",
  "service": "Payment",
  "event": "PROCESS_FAILED",
  "status": "FAILED",
  "topic": "order-confirmed",
  "partition": 1,
  "offset": "42",
  "messageKey": "ORD-1234",
  "attempt": 3,
  "maxRetries": 3,
  "errorReason": "Payment declined - insufficient funds",
  "nextTopic": "order-events-dlt",
  "timestamp": "2026-05-26T10:00:00.000Z"
}
Fieldบังคับความหมาย
messageIdYesid ของ event นี้
correlationIdYesid เดียวตลอดทั้ง flow
orderIdYesbusiness id ที่คนเข้าใจ
serviceYesInventory, Payment, …
eventYesRECEIVED … SENT_TO_DLT
statusYesสถานะที่เรากำหนดเอง
topic/partition/offsetYesตำแหน่งใน Kafka
attempt/maxRetriesแนะนำretry ครั้งที่เท่าไร
errorReasonเมื่อ failสาเหตุ
nextTopicไม่บังคับส่งต่อไปที่ไหน
timestampYesเวลา UTC
ตัวอย่างโค้ด

ใส่ Tracking ใน Worker แบบไม่รก

// lib/tracking.ts
export function createTracker(service: string, ctx: { topic: string; partition: number; message: KafkaMessage }) {
  const base = {
    service,
    topic: ctx.topic,
    partition: ctx.partition,
    offset: ctx.message.offset,
    messageKey: ctx.message.key?.toString(),
    correlationId: ctx.message.headers?.["x-correlation-id"]?.toString(),
  };
  return (event: TrackingEvent, extra: Partial<TrackingLog> = {}) =>
    trackingLog.write({ ...base, ...extra, event, status: STATUS_OF[event], timestamp: new Date().toISOString() });
}

// workers/consumer-payment.ts
eachMessage: async ({ topic, partition, message }) => {
  const track = createTracker("Payment", { topic, partition, message });
  await track("RECEIVED");
  // ...
  await track("RETRYING", { attempt, maxRetries: MAX_RETRIES, errorReason: String(err) });
  // ...
  await track("PUBLISHED", { nextTopic: "payment-result" });
}
การเขียน tracking log ล้มเหลว ต้องไม่ทำให้งานหลักล้ม — ห่อด้วย try/catch แล้ว log error แยก หรือเขียนแบบ async ลง buffer
ใช้งาน

ตอบคำถามจาก Tracking Log

คำถามวิธีตอบ
รับแล้วหรือยังหา event = RECEIVED ด้วย orderId
สำเร็จไหมlog ล่าสุดของ service เป็น PROCESS_SUCCESS / PUBLISHED
fail เพราะอะไรอ่าน errorReason ของ PROCESS_FAILED
retry กี่ครั้งattempt สูงสุดของ message นั้น
ไปถึงไหนแล้วquery ด้วย correlationId เรียงตามเวลา
-- timeline ของ order เดียว ข้ามทุก service
SELECT timestamp, service, event, status, attempt, error_reason
FROM tracking_log
WHERE correlation_id = 'ORD-1234'
ORDER BY timestamp;

-- order ที่ค้าง: รับแล้วแต่ยังไม่มีผลลัพธ์เกิน 10 นาที
SELECT correlation_id, service, MAX(timestamp) AS last_seen
FROM tracking_log
GROUP BY correlation_id, service
HAVING SUM(CASE WHEN event IN ('PUBLISHED','SENT_TO_DLT') THEN 1 ELSE 0 END) = 0
   AND MAX(timestamp) < NOW() - INTERVAL '10 minutes';

Monitoring

Consumer Lag: งานค้างอยู่เท่าไร

Metricความหมาย
committedOffsetgroup อ่านและ commit ถึงไหน
highWatermarkoffset ล่าสุดของ partition
lagจำนวน message ที่ยังอ่านไม่ถึง
memberIdworker instance ที่ดูแล partition
lag = highWatermark − committedOffset

lag เพิ่มต่อเนื่อง = producer ส่งเร็วกว่าที่ worker ทำทัน หรือ worker ล่ม/ช้า

// ใช้ใน /api/consumer-status
export async function getLag(groupId: string, topic: string) {
  const admin = kafka.admin();
  await admin.connect();
  try {
    const [committed] = await admin.fetchOffsets({ groupId, topics: [topic] });
    const latest = await admin.fetchTopicOffsets(topic);

    return latest.map(({ partition, high }) => {
      const c = committed.partitions.find((p) => p.partition === partition)?.offset ?? "-1";
      const done = c === "-1" ? 0 : Number(c);   // -1 = ยังไม่เคย commit
      return { partition, committedOffset: done, highWatermark: Number(high), lag: Number(high) - done };
    });
  } finally {
    await admin.disconnect();
  }
}
สรุป

สิ่งที่ต้องมีเพื่อ “รู้สถานะ” ของทุก message

  • ☐ correlationId ใน header ส่งต่อทุก service
  • ☐ log ทุก event: RECEIVED → … → PUBLISHED / SENT_TO_DLT
  • ☐ tracking log มี topic / partition / offset / key
  • ☐ attempt และ maxRetries เป็น field ไม่ใช่ข้อความ
  • ☐ เก็บใน DB / log platform ไม่ใช่ไฟล์ JSON
  • ☐ API ค้น timeline ตาม orderId
  • ☐ หน้าสถานะแสดง lag ต่อ partition + alert
  • ☐ สถานะ order เป็น lifecycle จริงทั้ง flow
