Setup

สร้าง Connection และ Queue (ใช้ร่วมกันทั้งโปรเจกต์)

// lib/queues.ts
import { Queue } from "bullmq";
import IORedis from "ioredis";

export const connection = new IORedis(process.env.REDIS_URL!, {
  maxRetriesPerRequest: null,   // จำเป็นสำหรับ Worker
});

export type EmailJob =
  | { type: "welcome"; userId: string }
  | { type: "order-confirmation"; orderId: string };

export const emailQueue = new Queue<EmailJob>("email", {
  connection,
  defaultJobOptions: {
    attempts: 5,
    backoff: { type: "exponential", delay: 2_000 },     // 2s, 4s, 8s, 16s ...
    removeOnComplete: { age: 24 * 3600, count: 1_000 }, // เก็บ 1 วัน / 1,000 รายการ
    removeOnFail: { age: 7 * 24 * 3600 },               // เก็บงานพัง 7 วันไว้ตรวจ
  },
});
ใส่ type ให้ข้อมูล job เสมอ (discriminated union) เพื่อให้ Worker รู้รูปแบบข้อมูลแน่นอน และเก็บข้อมูลให้เล็ก ส่งแค่ id ไม่ส่งทั้ง object
Producer

เพิ่ม Job จาก Next.js (Server Action / Route Handler)

// app/orders/actions.ts
"use server";
import { emailQueue } from "@/lib/queues";

export async function placeOrder(input: PlaceOrderInput) {
  const order = await api.post("/orders", input);

  await emailQueue.add(
    "order-confirmation",
    { type: "order-confirmation", orderId: order.id },
    {
      jobId: `order-confirmation:${order.id}`, // กันเพิ่มซ้ำ
      delay: 5_000,                            // รอ 5 วินาที
      priority: 1,                             // 1 = สำคัญสุด
    },
  );
  return order;
}

Consumer

Worker: ประมวลผล Job

// worker/email.worker.ts  (รันเป็น process แยก: node dist/worker.js)
import { Worker, UnrecoverableError } from "bullmq";
import { connection, type EmailJob } from "../lib/queues";

const worker = new Worker<EmailJob>(
  "email",
  async (job) => {
    switch (job.data.type) {
      case "order-confirmation": {
        const order = await api.get(`/orders/${job.data.orderId}`);
        if (!order) throw new UnrecoverableError("Order not found"); // ไม่ต้อง retry
        await job.updateProgress(50);
        const res = await mailer.send(orderConfirmationTemplate(order));
        return { messageId: res.id };                               // เก็บเป็น returnvalue
      }
      case "welcome":
        return mailer.send(welcomeTemplate(job.data.userId));
    }
  },
  { connection, concurrency: 10 },
);

worker.on("failed", (job, err) =>
  logger.error({ jobId: job?.id, attempts: job?.attemptsMade, err }, "email job failed"));
Error Handling

Retry, Backoff และ Error ที่ไม่ควร Retry

Transient error

API 503, timeout, rate limit ปลายทาง

→ throw ปกติ ให้ BullMQ retry ตาม backoff

Permanent error

ข้อมูลไม่มีแล้ว, input ผิด

→ throw new UnrecoverableError() ไป failed ทันที

Custom backoff

เช่น อ่าน header Retry-After

→ settings.backoffStrategy ใน Worker

attempt12345
exponential, delay 2sทันที+2s+4s+8s+16s → failed
Job อาจถูกทำซ้ำได้ (retry, stalled) ดังนั้น งานต้อง idempotent เช่น เช็คว่าส่งอีเมลออเดอร์นี้ไปแล้วหรือยังก่อนส่ง
Throughput

Concurrency และ Rate Limit

const worker = new Worker("sms", processor, {
  connection,
  concurrency: 20,                          // ทำพร้อมกัน 20 job ต่อ process
  limiter: { max: 100, duration: 1_000 },   // ทั้งคิวไม่เกิน 100 job/วินาที
});

// เจอ 429 จาก provider → พักทั้งคิวตามที่ provider บอก
if (res.status === 429) {
  await worker.rateLimit(retryAfterMs);
  throw Worker.RateLimitError();
}

Concurrency

งาน I/O (เรียก API, ส่งเมล) ตั้งสูงได้ 10–50 · งาน CPU หนัก (สร้าง PDF, resize รูป) ให้ต่ำและใช้ sandboxed processor

Rate limit เป็นระดับคิว

มีผลรวมทุก worker ทุกเครื่อง เหมาะกับ API ภายนอกที่จำกัดโควตา

Scheduling

งานตั้งเวลาด้วย Job Scheduler

// รันตอน worker start — upsert = เรียกซ้ำได้ ไม่สร้างซ้ำ
await reportQueue.upsertJobScheduler(
  "daily-sales-report",                                   // scheduler id
  { pattern: "0 8 * * *", tz: "Asia/Bangkok" },           // ทุกวัน 08:00 เวลาไทย
  { name: "daily-sales-report", data: { channel: "line" } },
);

await cleanupQueue.upsertJobScheduler(
  "purge-temp-files",
  { every: 15 * 60 * 1000 },                              // ทุก 15 นาที
);

// ยกเลิก
await reportQueue.removeJobScheduler("daily-sales-report");

ดีกว่า cron ในเครื่อง

มีหลาย worker ก็รันครั้งเดียว มี retry และดูประวัติได้

ระบุ timezone เสมอ

server มักเป็น UTC ถ้าไม่ใส่ tz งาน 08:00 จะรันตอน 15:00 เวลาไทย

Pitfalls

ข้อผิดพลาดที่พบบ่อย

ไม่ตั้ง removeOnComplete

job สำเร็จสะสมเป็นล้าน Redis memory เต็ม

ใส่ข้อมูลใหญ่ใน job.data

ส่งไฟล์/รูป base64 → เก็บใน storage แล้วส่ง key

ลืม maxRetriesPerRequest: null

Worker error ตอน Redis สะดุดชั่วคราว

ใช้ Redis cluster/managed ที่ eviction เปิดอยู่

job หายแบบไม่มี error

งาน CPU หนักใน main thread

event loop ค้าง lock หมดอายุ → job stalled ซ้ำ

ต้องการให้ .NET อ่าน job

BullMQ ไม่มี client .NET ทางการ ถ้าข้ามภาษา ใช้ RabbitMQ หรือให้ .NET เรียก API ฝั่ง Node เพื่อเพิ่ม job

Production Checklist

Checklist ก่อนขึ้น Production

  • ☐ Redis: noeviction, เปิด AOF, มี backup / HA
  • ☐ attempts + backoff ทุกคิว
  • ☐ removeOnComplete / removeOnFail
  • ☐ Job idempotent + ใช้ jobId กันซ้ำ
  • ☐ UnrecoverableError สำหรับ error ถาวร
  • ☐ Worker เป็น process/container แยก + graceful shutdown
  • ☐ concurrency / limiter เหมาะกับปลายทาง
  • ☐ Job Scheduler ระบุ tz: "Asia/Bangkok"
  • ☐ Bull Board ป้องกันด้วย auth
  • ☐ Alert: waiting สูง, failed เพิ่ม, Redis memory
