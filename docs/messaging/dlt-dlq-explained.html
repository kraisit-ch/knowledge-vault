DLT vs DLQ

DLT — Dead Letter Topic

ใช้กับ Kafka เพราะ Kafka เก็บข้อมูลเป็น topic

  • Kafka ไม่มีให้ในตัว โค้ดเราต้อง publish เข้าเอง
  • อ่านแล้วไม่หาย อยู่ตาม retention
  • หลายทีมอ่าน DLT เดียวกันได้ (เช่น ทีม support + dashboard)

DLQ — Dead Letter Queue

ใช้กับระบบที่เป็น คิว เช่น RabbitMQ, SQS, Azure Service Bus

  • มักมี ในตัว แค่ตั้งค่าที่คิว
  • รับไปแล้ว ack ก็หายจากคิว
  • RabbitMQ ทำผ่าน DLX → DLQ
ในทีมพูดว่า “DLQ” แทนทั้งสองแบบได้ แต่ในโค้ดและเอกสารของ Kafka ให้ใช้คำว่า DLT และตั้งชื่อ topic ลงท้าย -dlt เพื่อไม่สับสน · BullMQ ใช้สถานะ failed ทำหน้าที่แทน DLQ
กติกา

ข้อความแบบไหนควรเข้า DLQ

สถานการณ์ตัวอย่างส่งเข้า DLQ
Retry ครบแล้วยังล้ม (error ชั่วคราวที่ไม่หาย)payment gateway ล่มนานหลัง retry ครบ
ข้อมูลผิดรูปแบบJSON พัง, ขาด field บังคับทันที ไม่ต้อง retry
ผิดกฎธุรกิจ (ทางเลือก)สินค้าหมด, บัตรถูกปฏิเสธทันที หรือส่ง event “ไม่สำเร็จ” แทน

Kafka · DLT

Kafka: โค้ดเราต้องส่งเข้า DLT เอง

// เมื่อ retry ครบหรือข้อมูลผิด → ส่ง message เดิมไป DLT พร้อมสาเหตุ แล้วทำข้อความถัดไปต่อ
await producer.send({
  topic: "order-events-dlt",
  messages: [{
    key: message.key,                      // key เดิม (รักษาลำดับเมื่อ replay)
    value: message.value,                  // payload เดิม ห้ามแก้
    headers: {
      ...message.headers,                  // correlation id เดิม
      "x-failed-service": "payment-service",
      "x-error-type": "TRANSIENT",         // TRANSIENT / BUSINESS / INVALID
      "x-error-reason": "gateway timeout after 3 attempts",
      "x-retry-count": "3",
      "x-original-topic": topic,
      "x-original-partition": String(partition),
      "x-original-offset": message.offset,
      "x-failed-at": new Date().toISOString(),
    },
  }],
});

สร้าง DLT ล่วงหน้า

partition / replication เหมือน topic หลัก ปิด auto-create ใน production

Retention นานกว่า

14–30 วัน ให้มีเวลาตรวจและ replay

ส่ง DLT สำเร็จก่อน commit

ถ้าส่ง DLT ไม่ได้ อย่า commit offset ไม่งั้นข้อความหายจริง

RabbitMQ · DLX / DLQ

RabbitMQ: ตั้งค่าครั้งเดียว ทำงานอัตโนมัติ

payment queuex-dead-letter-exchange = payment.dlx
→ nack / เกิน delivery-limit / TTL →
payment.dlxDead Letter Exchange
→
payment.dlqรอคนตรวจ
// 1) สร้าง DLX + DLQ
await ch.ExchangeDeclareAsync("payment.dlx", ExchangeType.Fanout, durable: true);
await ch.QueueDeclareAsync("payment.dlq", durable: true, exclusive: false, autoDelete: false,
    arguments: new Dictionary<string, object?> { ["x-queue-type"] = "quorum" });
await ch.QueueBindAsync("payment.dlq", "payment.dlx", routingKey: "");

// 2) คิวหลักชี้ไปที่ DLX
await ch.QueueDeclareAsync("payment", durable: true, exclusive: false, autoDelete: false,
    arguments: new Dictionary<string, object?>
    {
        ["x-queue-type"] = "quorum",
        ["x-dead-letter-exchange"] = "payment.dlx",
        ["x-delivery-limit"] = 5,          // ส่งซ้ำเกิน 5 ครั้ง → DLQ
    });

// 3) ข้อมูลผิด → ไม่ต้องรอ ส่ง DLQ ทันที
await ch.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false);

RabbitMQ เติม header x-death ให้เอง (คิวต้นทาง, สาเหตุ เช่น rejected / expired / delivery_limit, จำนวนครั้ง) แต่ไม่รู้ข้อความ error ของแอป — log สาเหตุจริงไว้ใน tracking log ด้วย

BullMQ · Failed jobs

BullMQ: สถานะ failed ทำหน้าที่เป็น DLQ

// ลองครบ attempts แล้วยังล้ม → job อยู่ในสถานะ failed อัตโนมัติ
await emailQueue.add("order-confirmation", data, {
  attempts: 5,
  backoff: { type: "exponential", delay: 2_000 },
  removeOnFail: { age: 14 * 24 * 3600 },    // เก็บงานพังไว้ 14 วัน
});

// ข้อมูลผิด → ข้าม retry ไป failed ทันที
throw new UnrecoverableError("Order not found");

// ดูและสั่งทำใหม่
const failed = await emailQueue.getFailed(0, 50);
failed[0].failedReason;                      // สาเหตุ
await failed[0].retry();                     // ทำใหม่ทีละงาน
await emailQueue.retryJobs({ state: "failed" }); // ทำใหม่ทั้งหมด

ต้องการ DLQ แยกจริง ๆ

ฟัง event failed เมื่อ job.attemptsMade >= job.opts.attempts แล้ว add งานเข้า queue email-dead สำหรับทีม support

ห้ามลบงาน failed เร็วเกินไป

removeOnFail: true = ลบทิ้งทันที ไม่เหลือให้ตรวจ

ดูผ่านหน้าเว็บ

Bull Board แสดงงาน failed พร้อม stacktrace และปุ่ม Retry

Runbook

ขั้นตอนจัดการเมื่อมีข้อความเข้า DLQ

  1. แจ้งเตือน: มีข้อความใหม่เข้า DLQ หรือเกินเกณฑ์ (เช่น > 10 ใน 5 นาที) → แจ้ง LINE / Teams ของทีม
  2. ตรวจสอบ: เปิดหน้า DLQ Inspector ดูสาเหตุ, service ที่ล้ม, จำนวนครั้ง, correlation id
  3. จัดกลุ่มสาเหตุ: ระบบปลายทางล่ม / ข้อมูลผิด / บั๊กในโค้ด / ผิดกฎธุรกิจ
  4. แก้ต้นเหตุก่อน: รอระบบกลับมา, แก้ข้อมูล, deploy แก้บั๊ก
  5. ตัดสินใจ: replay กลับคิว/topic เดิม · แก้ข้อมูลแล้ว replay · หรือปิดงานพร้อมบันทึกเหตุผล
  6. บันทึก audit: ใครทำ, เมื่อไร, ทำอะไรกับข้อความไหน
ตั้งผู้รับผิดชอบดู DLQ ให้ชัด (เช่น เวรประจำสัปดาห์) — DLQ ที่ไม่มีใครดู ไม่ต่างจากถังขยะ
Replay

ส่งกลับไปทำใหม่อย่างปลอดภัย

ควรทำ

  • แก้ต้นเหตุก่อน replay ทุกครั้ง
  • consumer ต้อง idempotent (ทำซ้ำแล้วไม่ตัดเงินซ้ำ)
  • replay ทีละน้อย / จำกัดความเร็ว ไม่ให้ถล่มระบบปลายทาง
  • ใส่ header x-replayed-by, x-replayed-at
  • ทดลอง replay 1 รายการก่อน แล้วค่อยทำทั้งหมด

ไม่ควรทำ

  • replay ทั้ง DLQ ทันทีโดยไม่ดูสาเหตุ → กลับมาเข้า DLQ ใหม่หมด
  • แก้ payload เองโดยไม่บันทึกว่าแก้อะไร
  • ลบ DLQ ทิ้งเพื่อให้ dashboard เขียว
  • replay ข้อความเก่ามากที่สถานะธุรกิจเปลี่ยนไปแล้ว (เช่น order ถูกยกเลิก)

Checklist DLT / DLQ

  • ☐ ทุก consumer มีปลายทางเมื่อล้มเหลว (DLT / DLQ / failed)
  • ☐ ข้อมูลผิดไปทันที ไม่ต้อง retry
  • ☐ เก็บ payload เดิม + สาเหตุ + ต้นทาง + จำนวนครั้ง
  • ☐ retention ของ DLQ นานพอให้ตรวจ (14–30 วัน)
  • ☐ ผิดกฎธุรกิจที่เป็นเรื่องปกติ → ส่ง event ผลลัพธ์ ไม่ใช่ DLQ
  • ☐ แจ้งเตือนเมื่อมีของเข้า + มีผู้รับผิดชอบ
  • ☐ มีหน้าจอหรือ script สำหรับตรวจและ replay
  • ☐ consumer idempotent ก่อนเปิดให้ replay
  • ☐ audit ทุกการ replay / ปิดงาน
  • ☐ ทดสอบแล้วว่าข้อความไปถึง DLQ จริง
