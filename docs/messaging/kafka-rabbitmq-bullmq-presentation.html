📜 Apache Kafka

Kafka: “สมุดบันทึกเหตุการณ์” ขององค์กร

เหมาะเมื่อ

  • หลายทีม/หลายระบบต้องอ่าน event เดียวกัน
  • ต้องเก็บประวัติไว้อ่านซ้ำ เช่น คำนวณรายงานย้อนหลัง
  • ข้อมูลไหลเข้าปริมาณมหาศาล เช่น click, log, IoT
  • ส่งข้อมูลเข้า Data warehouse / Analytics

ไม่เหมาะเมื่อ

  • แค่อยากส่งอีเมล / สร้าง PDF เบื้องหลัง
  • ต้องการ delay, priority หรือ retry ทีละงาน
  • ทีมเล็กและไม่มีคนดูแล cluster
ศัพท์ที่จะเจอ: Topic · Partition · Consumer Group · อ่านเจาะลึก Kafka →
📮 RabbitMQ

RabbitMQ: “ศูนย์คัดแยกพัสดุ”

เหมาะเมื่อ

  • ส่งคำสั่งระหว่าง service เช่น .NET ↔ Node.js
  • ต้องคัดแยกตามเงื่อนไข เช่น ประเภทงาน, ภูมิภาค
  • ต้องการยืนยันว่าประมวลผลสำเร็จ (ack) ก่อนลบ
  • กระจายงานให้ worker หลายตัวช่วยกันทำ

ไม่เหมาะเมื่อ

  • ต้องอ่านข้อมูลย้อนหลังหลายวัน
  • ข้อมูลไหลเข้าปริมาณมหาศาลต่อเนื่องแบบ stream
  • ใช้เป็นที่เก็บข้อมูลระยะยาว (คิวบวม = ช้า)
ศัพท์ที่จะเจอ: Exchange · Ack · Dead Letter · อ่านเจาะลึก RabbitMQ →
📋 BullMQ

BullMQ: “กระดานมอบหมายงาน”

เหมาะเมื่อ

  • งานเบื้องหลังในแอป Node.js / Next.js
  • ส่งอีเมล, สร้าง PDF, import/export ไฟล์
  • ต้องการ retry อัตโนมัติ, หน่วงเวลา, ตั้งเวลา (cron)
  • เรียก API ภายนอกที่จำกัดจำนวนครั้ง (rate limit)

ไม่เหมาะเมื่อ

  • ระบบฝั่ง .NET ต้องรับงาน (ไม่มี client .NET ทางการ)
  • หลายระบบต้องอ่าน event เดียวกัน
  • ต้องเก็บประวัติไว้อ่านซ้ำ
งานเบื้องหลังฝั่ง .NET ที่ไม่ต้องข้ามระบบ ใช้ Hangfire / Hosted Service ได้ ไม่จำเป็นต้องใช้ BullMQ · อ่านเจาะลึก BullMQ →
ตัวอย่าง E-commerce

ระบบจริงใช้ร่วมกันได้ แต่ละตัวทำหน้าที่ของตัวเอง

  1. .NET Order API บันทึกออเดอร์ แล้วประกาศ OrderCreated ลง Kafka → Payment, Stock, Analytics อ่านไปทำงานของตัวเอง
  2. Stock service ส่งคำสั่ง ShipOrder ผ่าน RabbitMQ → คัดแยกไปคลังสินค้าตามภูมิภาค (TH / VN)
  3. Next.js เพิ่มงาน SendOrderEmail ลง BullMQ → worker ส่งอีเมล ถ้าล้มเหลวลองใหม่อัตโนมัติ
เริ่มต้นไม่ต้องใช้ครบ 3 ตัว ระบบส่วนใหญ่เริ่มด้วยตัวเดียวก็พอ เพิ่มตัวที่ 2 เมื่อมีปัญหาที่ตัวแรกแก้ไม่ได้จริง ๆ เท่านั้น เพราะทุกตัวที่เพิ่มคือภาระดูแล
Decision Guide

ตอบคำถามตามลำดับ ใช่ข้อแรกที่เจอ = ตัวที่ควรใช้

1. เป็นงานเบื้องหลังในแอป Node.js/Next.js (อีเมล, PDF, ตั้งเวลา)?
→
ใช่: BullMQ
2. หลายระบบต้องอ่าน event เดียวกัน / ต้องอ่านย้อนหลัง / ข้อมูลปริมาณมหาศาล?
→
ใช่: Kafka
3. ส่งคำสั่ง/งานข้าม service หรือข้ามภาษา และต้องคัดแยกปลายทาง?
→
ใช่: RabbitMQ
4. ไม่ใช่ทั้งหมด?
→
ยังไม่ต้องใช้ — เรียก API ตรงก็พอ

ถ้าองค์กรมีตัวใดอยู่แล้วและพอตอบโจทย์ ให้ใช้ของเดิมก่อน ลดภาระดูแลระบบ

ไม่ว่าเลือกตัวไหน

3 เรื่องที่ต้องออกแบบเสมอ

1

รับซ้ำได้ ไม่พัง

ทุกตัวอาจส่งข้อความซ้ำ ระบบปลายทางต้องทำให้ผลไม่ซ้ำ (Idempotency)

เช่น เช็คเลขออเดอร์ก่อนตัดเงิน

2

พังแล้วมีที่ไป

กำหนดการลองใหม่ (Retry) และที่พักงานที่ล้มเหลว (DLQ)

ห้ามวนลองใหม่ไม่สิ้นสุด

3

มองเห็นงานค้าง

มี Dashboard และแจ้งเตือนเมื่องานค้างเพิ่ม (Consumer Lag) หรือ error สูง

รู้ก่อนลูกค้าโทรมา

สรุป

จำ 3 บรรทัดนี้

Kafka

“เกิดอะไรขึ้นแล้ว” ให้หลายระบบอ่าน และอ่านย้อนหลังได้

Event ระดับองค์กร, Analytics, ข้อมูลปริมาณมาก

RabbitMQ

“ส่งคำสั่งไปให้ถูกที่” และยืนยันว่าทำสำเร็จ

สื่อสารระหว่าง service, คัดแยกตามเงื่อนไข, ข้ามภาษา

BullMQ

“งานเบื้องหลัง” ของแอป Node.js ให้ทำจนเสร็จ

อีเมล, PDF, ตั้งเวลา, retry อัตโนมัติ
