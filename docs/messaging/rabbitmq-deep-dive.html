Queue Types

เลือกประเภท Queue

Classic Queue

ประเภทเดิม เร็ว ไม่มี replication (ตั้งแต่ 4.0 ไม่มี mirrored queue แล้ว)

เหมาะกับ: ข้อมูลชั่วคราว, reply queue, งานที่หายได้

Quorum Queue แนะนำ

replicate ด้วย Raft ข้าม node ทนต่อ node ล่ม มี delivery limit

เหมาะกับ: งานธุรกิจทุกอย่างที่ห้ามหาย

Stream

log แบบ append-only อ่านซ้ำได้ คล้าย Kafka

เหมาะกับ: fan-out ปริมาณมาก, replay, เก็บย้อนหลัง

Reliability

4 จุดที่ทำให้ข้อความ ไม่หาย

  1. Durable exchange + Quorum queue อยู่รอดเมื่อ broker restart
  2. Persistent message (DeliveryMode = Persistent) เขียนลงดิสก์
  3. Publisher Confirms broker ยืนยันว่ารับและเก็บแล้ว ไม่ได้ confirm = ส่งใหม่
  4. Manual Ack consumer ack หลังประมวลผลสำเร็จเท่านั้น ถ้าตายก่อน ack ข้อความกลับเข้าคิว

mandatory: true

ถ้าไม่มี queue ไหนรับ broker ส่งคืน (BasicReturn) แทนที่จะทิ้งเงียบ ๆ

autoAck: true = เสี่ยง

ข้อความถูกลบทันทีที่ส่งถึง consumer ถ้าแอปล่มระหว่างทำ = หาย

.NET · Publisher

Publisher ด้วย RabbitMQ.Client 7 (async API)

var factory = new ConnectionFactory
{
    HostName = "rabbitmq", UserName = "shop-api", Password = config["Rabbit:Password"]!,
    VirtualHost = "/shop-prod", ClientProvidedName = "order-api",
};

// Connection: Singleton ทั้งแอป
await using var connection = await factory.CreateConnectionAsync();
await using var channel = await connection.CreateChannelAsync(
    new CreateChannelOptions(publisherConfirmationsEnabled: true,
                             publisherConfirmationTrackingEnabled: true));

await channel.ExchangeDeclareAsync("orders", ExchangeType.Topic, durable: true);

var props = new BasicProperties
{
    Persistent = true,
    ContentType = "application/json",
    MessageId = evt.EventId.ToString(),     // ใช้กันซ้ำฝั่ง consumer
    Type = nameof(OrderCreated),
};

// ใน v7 เมื่อเปิด confirmation tracking: await จะรอจน broker confirm (nack → throw)
await channel.BasicPublishAsync("orders", "order.created.th", mandatory: true,
    basicProperties: props, body: JsonSerializer.SerializeToUtf8Bytes(evt));
.NET · Consumer

Consumer: Manual Ack + Prefetch

await channel.BasicQosAsync(prefetchSize: 0, prefetchCount: 20, global: false);

var consumer = new AsyncEventingBasicConsumer(channel);
consumer.ReceivedAsync += async (_, ea) =>
{
    try
    {
        var evt = JsonSerializer.Deserialize<OrderCreated>(ea.Body.Span)!;
        using var scope = scopeFactory.CreateScope();
        await scope.ServiceProvider.GetRequiredService<OrderCreatedHandler>()
                   .HandleAsync(evt, ct);                      // ต้อง idempotent

        await channel.BasicAckAsync(ea.DeliveryTag, multiple: false);
    }
    catch (JsonException ex)
    {
        logger.LogError(ex, "Invalid message {MessageId}", ea.BasicProperties.MessageId);
        await channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: false); // → DLX
    }
    catch (Exception ex)
    {
        logger.LogWarning(ex, "Processing failed, will retry");
        await channel.BasicNackAsync(ea.DeliveryTag, multiple: false, requeue: true);  // quorum นับ delivery-limit
    }
};

await channel.BasicConsumeAsync("payment.order-created", autoAck: false, consumer: consumer);
Prefetch กำหนดจำนวนข้อความที่ส่งมาค้างที่ consumer ได้พร้อมกัน งานเร็ว → 50–200, งานหนัก → 1–10

DLX

exchange ปลายทางเมื่อข้อความถูก reject, หมด TTL หรือเกิน delivery limit

Retry แบบหน่วงเวลา

ใช้ queue รอที่มี TTL แล้ว dead-letter กลับคิวหลัก (เช่น 30s → 5m → 30m)

อย่า requeue วนทันที

ข้อความเสียจะวนไม่หยุด กิน CPU และบล็อกงานอื่น

Messaging Patterns

Pattern ที่ใช้บ่อย

Work Queue (Competing Consumers)

หลาย worker อ่าน queue เดียวกัน RabbitMQ แจกงานแบบ round-robin ตาม prefetch

ขยายด้วยการเพิ่ม worker ได้ทันที

Pub/Sub

แต่ละ service มี queue ของตัวเองผูกกับ exchange เดียวกัน

ทุก service ได้สำเนาของ event

RPC (Request/Reply)

ส่ง ReplyTo + CorrelationId แล้วรอคำตอบ

ใช้เท่าที่จำเป็น ถ้าต้องการ sync จริงใช้ HTTP/gRPC ง่ายกว่า

Library ระดับสูง

MassTransit / Wolverine / NServiceBus จัดการ retry, outbox, saga ให้

ตรวจ license ก่อนใช้ (MassTransit v9+ เป็น commercial)

Pitfalls

ข้อผิดพลาดที่พบบ่อย

เปิด connection ใหม่ทุก message

ช้ามากและ broker รับไม่ไหว → ใช้ connection ร่วม, channel ต่อ thread

ใช้ channel เดียวกันหลาย thread

channel ไม่ thread-safe สำหรับ publish พร้อมกัน

ไม่ตั้ง prefetch

broker ดันข้อความทั้งหมดไปที่ consumer ตัวแรก RAM เต็ม

ใช้ queue เป็นฐานข้อมูล

ข้อความค้างเป็นล้าน → ช้าลงมาก ควรมี TTL / max-length

ต้องการลำดับเคร่งครัด แต่มีหลาย consumer

ลำดับเพี้ยน → ใช้ single active consumer หรือ consistent-hash exchange

ไม่จัดการ connection หลุด

เปิด AutomaticRecoveryEnabled (ค่าเริ่มต้น) และ log เหตุการณ์ recovery

Production Checklist

Checklist ก่อนขึ้น Production

  • ☐ Cluster 3 nodes + Quorum queues
  • ☐ Publisher confirms + persistent + mandatory
  • ☐ Manual ack, prefetch เหมาะกับงาน
  • ☐ DLX/DLQ + delivery-limit + delayed retry
  • ☐ Consumer idempotent (เช็ค MessageId)
  • ☐ TLS, user แยกต่อ service, ปิด guest
  • ☐ Topology ประกาศด้วยโค้ด / definitions
  • ☐ Prometheus + alert: ready, unacked, DLQ, alarms
  • ☐ กำหนด max-length / TTL กันคิวบวม
  • ☐ ทดสอบ node ล่ม + consumer crash แล้ว
