Ordering

Message Key = ตัวกำหนด Partition และ ลำดับ

กฎสำคัญ

  • Kafka รับประกันลำดับ ภายใน partition เดียว เท่านั้น
  • message ที่มี key เดียวกัน → ไป partition เดียวกันเสมอ (hash ของ key)
  • ไม่มี key → กระจายไปหลาย partition ลำดับไม่แน่นอน

เลือก key อย่างไร

  • ต้องการลำดับต่อ “อะไร” ให้ใช้สิ่งนั้นเป็น key
  • ออเดอร์ → orderId, บัญชี → accountId
  • ระวัง hot partition: key ที่ข้อมูลเยอะผิดปกติ (เช่นร้านค้าใหญ่ร้านเดียว)

Delivery Guarantees

At-most-once · At-least-once · Exactly-once

At-most-once

commit offset ก่อนประมวลผล

ถ้าพังกลางทาง = ข้อมูลหาย

At-least-once แนะนำ

ประมวลผลเสร็จแล้วค่อย commit

ถ้าพัง = อาจได้ซ้ำ → consumer ต้อง idempotent

Exactly-once

Transactions + read_committed

ได้ผลเฉพาะ Kafka → Kafka ถ้าเขียนลง DB ภายนอกยังต้อง idempotent อยู่ดี

ออกแบบให้ “รับซ้ำได้โดยไม่เกิดผลซ้ำ” (Idempotent Consumer) ง่ายและทนทานกว่าไล่ทำ Exactly-once ทุกที่
.NET · Producer

Producer ด้วย Confluent.Kafka

ห้ามสร้าง producer ใหม่ทุก request และเรียก producer.Flush() ตอนแอปปิด เพื่อส่ง message ที่ค้างใน buffer ให้หมด
var config = new ProducerConfig
{
    BootstrapServers = "kafka-1:9092,kafka-2:9092,kafka-3:9092",
    Acks = Acks.All,
    EnableIdempotence = true,          // กันซ้ำตอน retry
    LingerMs = 5,                      // รวม batch เล็กน้อยเพื่อ throughput
    CompressionType = CompressionType.Zstd,
};

// ลงทะเบียนเป็น Singleton — producer หนึ่งตัวใช้ทั้งแอป (thread-safe)
using var producer = new ProducerBuilder<string, string>(config).Build();

var evt = new OrderCreated(order.Id, order.CustomerId, order.Total, DateTimeOffset.UtcNow);
var result = await producer.ProduceAsync("orders.created", new Message<string, string>
{
    Key = order.Id.ToString(),                   // ลำดับต่อออเดอร์
    Value = JsonSerializer.Serialize(evt),
    Headers = new Headers { { "event-type", "OrderCreated"u8.ToArray() } },
}, ct);

_logger.LogInformation("Produced {OrderId} to {TopicPartitionOffset}", order.Id, result.TopicPartitionOffset);
.NET · Consumer

Consumer แบบ At-least-once ใน BackgroundService

Consume() เป็น blocking call ให้รัน loop ใน Task.Run หรือ thread แยก และเรียก consumer.Close() ตอน shutdown เพื่อออกจาก group อย่างสุภาพ
var config = new ConsumerConfig
{
    BootstrapServers = "kafka-1:9092",
    GroupId = "payment-service",
    AutoOffsetReset = AutoOffsetReset.Earliest,
    EnableAutoCommit = false,                       // commit เองหลังประมวลผลสำเร็จ
    PartitionAssignmentStrategy = PartitionAssignmentStrategy.CooperativeSticky,
};

using var consumer = new ConsumerBuilder<string, string>(config).Build();
consumer.Subscribe("orders.created");

while (!stoppingToken.IsCancellationRequested)
{
    var cr = consumer.Consume(stoppingToken);
    var evt = JsonSerializer.Deserialize<OrderCreated>(cr.Message.Value)!;

    using var scope = _scopeFactory.CreateScope();  // DbContext เป็น Scoped
    var handler = scope.ServiceProvider.GetRequiredService<OrderCreatedHandler>();
    await handler.HandleAsync(evt, stoppingToken);  // ต้อง idempotent

    consumer.Commit(cr);                            // commit หลังสำเร็จเท่านั้น
}
Error Handling

Kafka ไม่มี Retry/DLQ ในตัว ต้องออกแบบเอง

→ fail →
orders.created.retry-1m
→ fail →
orders.created.retry-10m
→ fail →
orders.created.dlq

Transient error

DB timeout, API 503 → retry ใน process 2–3 ครั้ง (exponential backoff) ก่อนส่งไป retry topic

Poison message

JSON ผิด, ข้อมูลไม่ครบ → ส่ง DLQ ทันที ห้ามวนซ้ำ ไม่งั้น partition ค้างทั้งแถว

DLQ ต้องมีคนดู

แนบ header: error, stack, original topic/offset และมี alert + เครื่องมือ replay

Pitfalls

ข้อผิดพลาดที่พบบ่อย

ใช้ Kafka เป็น job queue

งานที่ต้อง delay, priority, retry ทีละ job → BullMQ / RabbitMQ เหมาะกว่า

Consumer ช้าเกิน max.poll.interval.ms

ถูกเตะออกจาก group → rebalance วนไม่จบ ลด batch หรือแยกงานหนักออก

Auto commit + ประมวลผล async

offset ถูก commit ก่อนงานเสร็จ → ข้อมูลหายเมื่อ crash

Message ใหญ่เกินไป

ค่าเริ่มต้น ~1MB เก็บไฟล์ใน object storage แล้วส่งแค่ URL

ไม่มี key แต่ต้องการลำดับ

event ของออเดอร์เดียวกันมาสลับลำดับ

เปลี่ยน schema แบบไม่ backward compatible

consumer เวอร์ชันเก่าพังทันที

Production Checklist

Checklist ก่อนขึ้น Production

  • ☐ 3 brokers, replication.factor=3, min.insync.replicas=2
  • ☐ Producer: acks=all, idempotence เปิด
  • ☐ Key ถูกเลือกตามลำดับที่ต้องการ
  • ☐ Consumer commit หลังประมวลผล + idempotent
  • ☐ มี retry topic / DLQ + alert
  • ☐ Outbox สำหรับ event ที่มาจากการเขียน DB
  • ☐ Schema Registry / versioning ของ event
  • ☐ TLS + SASL และ ACL แยกสิทธิ์ต่อ service
  • ☐ Dashboard: lag, URP, disk, rebalance
  • ☐ ทดสอบ broker ล่ม และ consumer restart แล้ว
